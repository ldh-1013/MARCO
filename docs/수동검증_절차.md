# 수동 검증 절차 — 파문 · 밸브 · 라운드 · 태그

> 대상: `Assets/Scenes/Game.unity` Play 모드
> 자동 테스트로 덮을 수 없는 영역(렌더링·Physics·프레임률·네트워크)만 다룬다. 로직은 EditMode 테스트 176케이스가 담당한다.
> 반복 가능하도록 절차를 고정해 둔 문서다 — 스프린트마다 이 순서대로 확인한다.

---

## 0. 준비

1. `Assets/Scenes/Game.unity`를 열고 Play
2. Hierarchy에서 `PulseSystem` 선택 → `Local Pulse Pipeline Behaviour` · `Pulse Visual Renderer` · `Valve Objective Tracker`가 붙어 있는지 확인. `Player`에는 `Valve Interactor`가 있어야 한다
3. Console 필터: `[Pulse]`(파문, 상세 로그 기본 꺼짐 — §5) / `[Valve]`(밸브) / `[Round]`(라운드 진행·판정) / `[Escape]`(탈출) / `[Tag]`(태그)

## 1. ⚠️ 가장 중요한 전제 — 청취점은 스폰 지점에 고정돼 있다

**시각 효과는 스폰 지점 주변에서만 보인다. 이것은 버그가 아니라 현재 구조상 당연한 동작이다.**

지금은 로컬 단일 클라이언트라 "남의 소리를 듣는 다른 플레이어"가 없다. 그래서 `LocalPulsePipelineBehaviour`가 **Start 시점의 플레이어 위치(스폰 지점, 약 `12, 0.05, 27`)에 가상 청취자 하나를 고정**해 두고 그 청취자 기준으로 판정한다(임시 스모크 리그).

판정 경로는 이렇다:

```
발소리 발생 (플레이어 현재 위치, 반경 2m/6m)
  → SoundPulseResolver.Resolve(pulse, 청취자=스폰지점)
  → straightDist > baseRadius 이면 즉시 null 반환   ← Core의 1차 컷
  → null이면 델리버리 자체가 없음
  → 렌더러는 그릴 것이 없음
```

즉 **플레이어가 스폰 지점에서 걷기 2m / 질주 6m를 벗어나면 아무것도 안 보이는 게 정상**이다. 렌더러의 문제가 아니라 Core의 거리 게이트가 먼저 걸러내는 것이며, 이 동작은 EditMode 테스트 `LocalPulsePipelineExpiryTests.SourceWalkingAwayFromFixedListener_LaterPulsesNeverAppear`가 이미 고정해 두었다.

> **따라서 아래 모든 절차는 "스폰 지점 반경 6m 이내"에서 수행해야 한다.**
> 실제 "멀리 있는 남의 발소리를 듣는" 기능은 네트워크 스프린트에서 청취자가 실제 원격 플레이어로 바뀔 때 완성된다.

**팁**: 스폰 지점을 잃어버렸으면 Play를 다시 시작하거나, Scene 뷰에서 `Player`의 시작 위치를 확인한다. Console 첫 줄에 `[Pulse] 디버그 청취점 고정: (12.0, 0.1, 27.0)` 이 찍힌다.

## 2. 기본 동작 — 파문 링이 보이는가

1. 스폰 지점에서 **제자리 또는 2m 이내로 조금씩** WASD 이동
2. 발소리마다 발밑에서 **원형 링이 퍼져 나가며 옅어지는지** 확인
3. `Shift` 질주 시 링이 **더 크게(6m) 퍼지는지** 확인

기대: 걷기는 작고 촘촘하게(0.4초 주기), 질주는 크고 느리게(0.8초 주기).

---

## 3. 차폐 검증 — GAP-2 분기가 눈에 보이는가 (T8의 핵심)

이번 스프린트에서 **처음으로** "차폐돼서 방향만 아는 것"과 "아예 안 들리는 것"이 시각적으로 구별된다.

1. 스폰 지점(로비) 근처에서 발소리를 내며 링이 보이는 것을 확인
2. **스폰 지점에서 6m를 벗어나지 않으면서** 벽 뒤(로비 벽 모서리 안쪽 등)로 이동
3. 화면 표시가 어떻게 바뀌는지 관찰

| 상황 | 기대 표현 |
|---|---|
| 벽 없이 트여 있음 | 발생 지점에 **월드스페이스 링** |
| 벽에 가려짐(반경 안) | 링 없이 **화면 가장자리 8방위 인디케이터(◆)** 만 |
| 반경 밖 | **아무것도 없음** |

세 번째와 두 번째가 구별되는 것이 이번 작업의 목표다. 인디케이터는 카메라가 바라보는 방향 기준으로 배치되므로, 제자리에서 마우스를 돌리면 ◆ 가 화면 가장자리를 따라 도는 것을 볼 수 있다.

## 4. 자연 소멸 확인 — Disappeared 없이 스스로 사라지는가

**배경**: 파문이 지속시간을 다 채우고 자연히 끝날 때는 `Disappeared` 신호가 오지 **않는다**(T7 설계, 스프린트 3 버그 조사에서 확정). 그래서 렌더러는 자체 타이머로 사라져야 한다. 이게 깨지면 파문이 화면에 영원히 남는다.

**절차**:
1. 스폰 지점에서 **한 걸음만 움직여 발소리 하나를 낸 뒤 즉시 멈춘다**
2. 가만히 서서 링을 관찰한다
3. 걷기 발소리는 **0.4초**, 질주는 **0.8초** 안에 완전히 사라져야 한다

기대: 링이 최대 반경까지 퍼지면서 투명해지다가 사라진다. **1초 넘게 남아 있으면 회귀 버그다.**

## 5. 색맹 모드 전환 (§19)

**방법 A — 디버그 키 (권장, 코드/인스펙터 수정 불필요)**

Play 중에 **`C` 키**를 누른다. Console에 `[Pulse] 색맹 모드 켜짐/꺼짐 (§19)` 이 찍히고, 그 즉시 파문 색이 바뀐다.

| 모드 | 러너 파문 색 |
|---|---|
| 기본 | 민트 `#35F0D0` |
| 색맹 | 노랑 `#F2E205` |

색 전환을 확실히 보려면 파문이 떠 있는 동안 눌러야 한다 — 발소리를 내면서 누르거나, `P` 키로 30개를 띄운 직후 누르면 확실하다.

**방법 B — 인스펙터**

`PulseSystem` → `Pulse Visual Renderer` → `Colorblind Mode` 체크박스. Play 중에 토글해도 즉시 반영된다.

**키 변경**: `PulseSystem` → `Local Pulse Pipeline Behaviour` → `Colorblind Toggle Key` 에서 바꿀 수 있다.

## 6. 성능 확인 (§15.5 동시 30개 @ 60fps)

1. `Game` 뷰에서 **Stats** 패널을 켠다(우상단 Stats 버튼)
2. Play 중 **`P` 키**를 누른다 → 청취점 주변에 파문 30개가 한꺼번에 생성된다
3. Stats의 FPS와 Console 로그의 프레임 시간을 확인한다

Console에 다음이 찍힌다:
```
[Pulse] 스트레스 테스트: 30개 생성 (활성 시각 오브젝트 N, 프레임 16.7ms)
```

기대: 60fps = 16.7ms 이하 유지. 파문 개수는 `Stress Test Pulse Count` 로 조절할 수 있다.

**더 정밀하게 보려면**: `Window > Analysis > Profiler`를 열고 `P` 를 누른 뒤 해당 프레임을 선택 → `GC.Alloc` 이 프레임당 0에 가까운지, `Camera.Render`/`GUI.Repaint` 중 어디에 시간이 쏠리는지 본다. (정밀 수치 실측 자체는 T6 스코프)

## 7. 밸브 상호작용 (스프린트 5, §6.1)

**밸브 위치**: 스폰(로비)에서 상당히 멀다. §10.1 배치 기준 — 기계실 `(36.4, 1, 19)`, 라이프가드실 `(34.4, 1, 11)`, 보일러 통로 `(40.5, 1, 13)`. 주황색(#FFB84D) 큐브를 찾아 이동한다.

### 7-1. 홀드 진행

1. 밸브에 **2.5m 이내**로 접근(GAP-10 결정값 — `ValveInteractor.Interaction Range`로 조정 가능)
2. **E를 누른 채 유지**
3. Console에 다음이 순서대로 찍히는지 확인:
```
[Valve] 기계실 밸브 회전 시작 (§6.1)
[Valve] 기계실 밸브 회전 중 17%
[Valve] 기계실 밸브 회전 중 33%
...
[Valve] 기계실 밸브 개방 완료
[Valve] 개방 1/3 — WinCondition: InProgress
```
기대: **3초**(§6.2 4인 기준) 만에 완료. 진행률 로그 간격은 `Progress Log Interval`(기본 0.5초).

### 7-2. 취소 조건 (GAP-9)

| 시도 | 기대 |
|---|---|
| 홀드 도중 **E를 뗀다** | `취소 — E를 뗌, 진행도 0으로 리셋` |
| 홀드한 채 **2.5m 밖으로 걸어 나간다** | `취소 — 범위 이탈, 진행도 0으로 리셋` |
| 홀드한 채 **범위 안에서만 움직인다** | **취소되지 않고 계속 진행** ← 기획서에 "이동 시 취소" 문구가 없어 규칙을 만들지 않았다 |

취소 후 다시 E를 누르면 **0%부터** 다시 시작한다(§6.1 부분 진행 저장 없음).

### 7-3. 역할 제약 (GAP-5)

1. Play를 멈추고 `Player` → `First Person Controller` → **`Role`을 `Echo`로 변경**
2. Play 후 밸브에서 E 홀드
3. 기대: `[Valve] … 상호작용 거부 — 역할 Echo (GAP-5: 메아리는 밸브 조작 불가)` 로그만 뜨고 **진행률이 전혀 오르지 않음**
4. 확인 후 `Role`을 `Runner`로 되돌린다

> 술래(`Seeker`)는 밸브를 돌릴 수 있다 — 기획서가 금지한 것은 메아리뿐이다.

### 7-4. 밸브 소음 (§5.1, 12m)

밸브 회전을 시작하면 **12m 반경 파문**이 발생한다(§6.1 "의도된 유인 장치"). 다만 §1의 청취점 제약 때문에, 스폰 지점에서 멀리 떨어진 밸브의 파문은 **화면에 보이지 않는 것이 정상**이다. 발생 여부는 `Log Deliveries`를 켜서 Console로 확인하거나, 네트워크 스프린트에서 청취자가 실제 플레이어로 바뀐 뒤에 눈으로 확인한다.

### 7-5. 승패 판정 연결 (§6.3)

밸브 3개를 모두 열면:
```
[Valve] 개방 3/3 — WinCondition: InProgress
[Valve] 밸브 전체 개방 — 배수로 게이트 Open, 탈출 가능 (§6.1). …
```

`InProgress`가 맞다 — **탈출·태그·라운드 타이머가 아직 미구현**이라 §6.3의 승리 조건이 성립하지 않는다. 판정식 자체를 확인하려면 `PulseSystem` → `Valve Objective Tracker` → `Runners Escaped`를 **1로 바꾼 뒤** 밸브를 열어본다 → `WinCondition: RunnersWin` 이 나와야 한다.

## 8. 라운드 진행 — 탈출과 시간 초과 (스프린트 6, §6.2/§6.3)

이제 **게임이 끝난다.** Play 시작 시 Console에 다음이 찍힌다:
```
[Round] 라운드 시작 — 제한시간 600초 (§6.2), 상태 InGame
```
이후 30초마다 `[Round] 남은 시간 …초`.

### 8-1. 게이트가 닫힌 상태에서는 탈출 불가 (§6.1)

1. 밸브를 **열지 않은 채** 배수로 출구의 탈출 지점(주황 발판, `40.5, 0.3, 5`)으로 이동
2. 기대: `[Escape] 배수로 게이트가 아직 닫혀 있다 — 밸브 3개를 모두 열어야 탈출할 수 있다 (§6.1)`
3. 라운드는 계속 진행된다

### 8-2. 러너 승리 경로 (§6.3) — 이번 스프린트로 처음 성립

1. 밸브 3개를 모두 연다(§7 절차) → `[Valve] 밸브 전체 개방 — 배수로 게이트 Open, 탈출 가능 (§6.1)`
2. 탈출 지점으로 이동
3. 기대:
```
[Round] 탈출 — playerId=1 (누적 1명)
[Round] 라운드 종료 — 판정: RunnersWin (밸브 3/3, 탈출 1명, 남은 시간 …초) → 상태 RoundEnd
```
`InGame → RoundEnd` 전이(§15.4)까지 로그로 확인된다.

### 8-3. 시간 초과 → 술래 승리

전체 10분을 기다리기 어려우므로 `PulseSystem` → `Round Coordinator` → **`Round Duration Seconds`를 10~20초로 줄여** 테스트한다.

기대:
```
[Round] 제한시간 종료 (§6.2)
[Round] 라운드 종료 — 판정: SeekerWin (밸브 0/3, 탈출 0명, 남은 시간 0.0초) → 상태 RoundEnd
```

**만료는 정확히 1회만** 발생해야 한다 — `제한시간 종료` 로그가 두 번 이상 찍히면 회귀 버그다.

### 8-4. 판정 우선순위 (§6.3 if/else 순서)

짧은 제한시간(예: 20초)으로 두고, **시간이 끝나기 전에 밸브 3개 개방 + 탈출**을 완료해 본다.
기대: 시간이 그 뒤에 만료돼도 판정은 `RunnersWin`으로 **고정**된다(탈출은 취소되지 않는 달성).

### 8-5. 태그 승리 경로는 아직 닫혀 있다

태그 판정(§14.1)은 다음 스프린트다. §6.3의 `allRunnersTagged` 분기를 확인하려면 `Round Coordinator` → **`All Runners Tagged`** 를 체크한다 → 즉시 `SeekerWin`.

## 9. 태그 판정 (스프린트 7, §3.1)

**대역 도망자**: 로컬은 플레이어가 한 명뿐이라 태그할 상대가 없다. 그래서 로비 인근에 민트색 캡슐 3개(`Runner_A/B/C`, 대략 `15,27` · `12,25.5` · `16.5,25`)를 대역으로 놓았다 — **실제 게임플레이 기능이 아니라 검증용**이다.

> ⚠️ **스프린트 15에서 이 대역 3개는 비활성화됐다**(실제 원격 플레이어로 대체 완료). 이 절(§9)의 로컬 태그 절차를 수행하려면 Hierarchy에서 `Runner_A/B/C`를 **직접 활성화**해야 한다. 비활성 상태에서는 `OnEnable`이 호출되지 않아 `TagTargetRegistry`에 등록되지 않으므로 태그 대상이 아예 없다.
>
> 되살릴 때 주의: 대역이 등록되면 GAP-19 전원태그 모집단에 다시 포함되므로, 네트워크 테스트(§13·§15) 전에는 반드시 다시 비활성화할 것.

### 9-1. 준비 — 술래 역할로 전환

1. Play를 멈추고 `Player` → `First Person Controller` → **`Role`을 `Seeker`로 변경**
2. Play (태그는 술래만 할 수 있다 — §3.1)

### 9-2. 태그 발생

1. 대역 도망자 캡슐에 **1.2m 이내**로 접근
2. 기대: 즉시 `[Tag] 태그 — targetId=101 메아리로 전환 (§3.1) [1/3]`
   - **키 입력 불필요** — §3.1이 "접촉 트리거, 1회 접촉 즉시 확정"이라 접근만으로 발동한다
3. 같은 캡슐에 다시 접근해도 **추가 로그가 없어야 한다**(이미 메아리 = 태그 불가)

### 9-3. 일부만 태그 — 라운드가 끝나지 않는지

1과 2번 캡슐만 태그하고 멈춘다.
기대: `[2/3]`까지만 찍히고 **라운드 종료 로그가 없다**.

### 9-4. 전원 태그 → 즉시 술래 승리 (시간 만료를 기다리지 않음)

3번째 캡슐까지 태그한다.
```
[Tag] 태그 — targetId=103 메아리로 전환 (§3.1) [3/3]
[Round] 라운드 종료 — 판정: SeekerWin (밸브 0/3, 탈출 0명, 태그 3/3, 남은 시간 ...초) → 상태 RoundEnd
```
**남은 시간이 넉넉히 남아 있는데도 즉시 종료되는 것**이 핵심이다.

### 9-5. 혼재 경계 케이스 (가장 중요)

탈출과 태그가 섞였을 때 §6.3 우선순위를 확인한다.

1. `Role`을 `Runner`로 되돌리고 밸브 3개를 모두 연다
2. 탈출 지점으로 가서 탈출 → `RunnersWin`

§6.3의 if/else 순서상 **탈출(첫 분기)이 태그보다 우선**한다. 탈출은 게이트 개방 이후에만 가능하므로, 탈출이 성립하는 순간 이미 러너 승리 조건이 충족돼 있다. 이 우선순위는 EditMode 테스트 `EscapeWithValvesComplete_BeatsRemainingTags`가 고정한다.

> 참고: 대역 도망자는 움직이지 않으므로 "일부 탈출 + 일부 태그"를 로컬에서 동시에 만들기는 어렵다. 해당 경계는 EditMode 테스트로 검증했다.

### 9-6. 태그 없이 §6.3 술래 분기만 확인하려면

`Round Coordinator` → **`Force All Runners Tagged`** 체크 → 즉시 `SeekerWin`.

## 10. 네트워크 플레이어 구성 (스프린트 8, §14) — 자동화 도구 + 에디터 GUI 절차

> **코드 계층(Step 1~3)은 이미 완료·검증됐다.** `ILocalControlGate`(Core), 소유권 게이팅(`FirstPersonController`), `PlayerOwnershipGate`(Net), 지연 바인딩(`LocalPlayerRegistry`)이 전부 컴파일·테스트 통과 상태다. 남은 것은 **에디터에서만 안전하게 할 수 있는 자산 작업**(프리팹화 + FishNet 컴포넌트 부착 + 스폰 배선)이다.
>
> **왜 원래 GUI로 했는가**: `NetworkObject`는 `PrefabId`·`AssetPathHash`·`NetworkBehaviours` 목록 등 **에디터가 생성하는 값**을 직렬화 필드로 갖는다. 손으로 YAML을 쓰면 이 값들이 어긋나 임포트가 깨질 위험이 크다. GUI로 하면 전부 자동 생성된다.
>
> **지금은 원클릭 자동화 도구로 대체됐다.** `Assets/_Project/Editor/NetworkPlayerSetupTool.cs`가 아래 10-1~10-5의 GUI 조작을 `PrefabUtility`·`AddComponent`·`SerializedObject` 등 **정상 UnityEditor API 호출 경로**로 그대로 재현한다. `PrefabId`·`AssetPathHash` 같은 FishNet 자동 생성 값은 스크립트가 손으로 채우지 않고, 컴포넌트 부착·프리팹 저장 시 `NetworkObject.OnValidate`/`Reset`이 스스로 채우도록 맡긴다 — GUI로 했을 때와 동일한 경로다.

### 10-0. 자동화 도구로 실행 (권장)

1. **작업 전 백업 권장**: `Assets/Scenes/Game.unity`를 복사해둔다. 씬 변경(오브젝트 생성·삭제)은 Ctrl+Z로 되돌릴 수 있지만, 프리팹·에셋 변경(`Player.prefab`, `DefaultPrefabObjects.asset`)은 에디터 Undo로 되돌아가지 않는다.
2. 메뉴 **`Tools → MARCO → Setup Network Player`** 클릭
3. 확인 대화상자에서 **계속** 선택
4. Console에 각 단계 로그(NetworkManager 배치 → Player 프리팹화 → 컴포넌트 부착 → PlayerSpawner 배선 → 씬 인스턴스 제거)와 마지막 검증 안내가 순서대로 찍히는지 확인
5. **씬 저장(Ctrl+S)** — 도구는 씬을 dirty로 표시만 하고 저장은 하지 않는다

도구는 **재실행해도 안전하다(idempotent)**: 이미 존재하는 `NetworkManager`/`Player.prefab`/컴포넌트는 건드리지 않고 재사용하며, 이미 등록된 스폰 프리팹은 중복 추가하지 않는다.

아래 10-1~10-5는 도구가 내부적으로 수행하는 작업을 그대로 서술한 것이다 — 도구가 실패하거나 수동으로 하나씩 확인하고 싶을 때 참고한다.

### 10-1. NetworkManager 오브젝트 배치

1. Hierarchy 빈 곳 우클릭 → **Create Empty**, 이름 `NetworkManager`
2. Inspector **Add Component** → `Network Manager` 검색해 추가
   - 하위 매니저(ServerManager·ClientManager·TransportManager 등)는 **런타임에 자동 생성**되므로 지금 붙이지 않아도 된다(NetworkManager.cs가 `GetOrCreateComponent`로 만든다)
3. 같은 오브젝트에 **Add Component** → `Tugboat` 추가
   - Tugboat는 FishNet 기본 로컬 트랜스포트다. Steam(FishyFacepunch) 전환은 **이번 스코프 아님**(§14.1 스택은 최종적으로 Steam이지만, 로컬 루프백 검증이 먼저다)
   - 기본값 그대로 둔다: `Port 7770`, `Client Address localhost` — **로컬 테스트에 이대로 맞다**
4. 같은 오브젝트에 **Add Component** → `Player Spawner` 추가

**확인**: NetworkManager 컴포넌트의 `Spawnable Prefabs` 필드를 본다.
- 비어 있으면 Console에 안내가 뜨고, **에디터가 `Assets/DefaultPrefabObjects.asset`을 자동으로 물린다**(이미 존재함). 자동으로 안 채워지면 그 에셋을 직접 드래그해 넣는다.

### 10-2. 기존 Player를 프리팹으로 만들기

현재 씬의 `Player` 오브젝트에는 이미 필요한 게 다 붙어 있다(CharacterController·FirstPersonController·TagDetector·ValveInteractor + 자식 PlayerCamera). 이걸 그대로 프리팹화한다.

1. `Assets/_Project/` 아래에 `Prefabs` 폴더 생성(우클릭 → Create → Folder)
2. Hierarchy의 **`Player`를 그 폴더로 드래그** → "Original Prefab" 선택(프리팹 생성)
   - 씬의 Player는 파란색(프리팹 인스턴스)으로 바뀐다. 아직 씬에서 지우지 않는다

### 10-3. 프리팹에 FishNet 컴포넌트 부착

`Assets/_Project/Prefabs/Player.prefab`을 더블클릭해 **프리팹 편집 모드**로 연다.

**① NetworkObject** (루트에 추가)
1. 루트 `Player` 선택 → **Add Component** → `Network Object`
2. 값은 **전부 기본값 그대로 둔다.** `PrefabId`·`AssetPathHash`는 에디터가 자동 채우므로 **건드리지 않는다**

**② NetworkTransform** (루트에 추가) — 위치/회전 동기화의 핵심
1. 루트 `Player` 선택 → **Add Component** → `Network Transform`
2. **반드시 확인할 값**:
   | 필드 | 설정 | 이유 |
   |---|---|---|
   | `Synchronize Position` | ✅ 켜짐(기본) | 이동 동기화 |
   | `Synchronize Rotation` | ✅ 켜짐(기본) | 시점 회전 동기화 |
   | `Synchronize Scale` | ⬜ 꺼도 됨 | 스케일은 안 변한다 — 대역폭 절약 |
3. 나머지(보간·스냈핑 등)는 **기본값 그대로**. 튜닝은 실제로 끊겨 보일 때 하면 된다

**③ PlayerOwnershipGate** (루트에 추가) — 우리가 만든 소유권 게이트
1. 루트 `Player` 선택 → **Add Component** → `Player Ownership Gate` 검색해 추가
2. **설정할 값 없음.** 이 컴포넌트는 `Awake`에서 `GetComponentsInChildren<ILocalControlGate>()`로 `FirstPersonController`를 스스로 찾아 소유권을 전달한다 — 인스펙터 배선이 필요 없게 설계했다

**④ Body(시각적 몸체) — 원격 플레이어가 화면에 보이려면 필요**
`Player.prefab`에 자식 오브젝트 `Body`가 이미 포함돼 있다(캡슐 Mesh, `CharacterController`와 동일한 반경 0.35·높이 1.8에 맞춘 스케일 `{0.7, 0.9, 0.7}`, 로컬 위치 `{0, 0.9, 0}`, `GrayboxWall` 머티리얼 재사용). 별도 작업 불필요 — 프리팹을 열어보면 캡슐이 이미 붙어 있다.

**의도적으로 안 한 것 — 자기 시점 컬링**: 이번 스프린트 목적은 "원격 플레이어가 최소한 보이긴 하는지" 확인이라, 로컬 플레이어 본인의 카메라에서 자기 캡슐을 안 보이게 하는 처리(레이어+카메라 Culling Mask)는 하지 않았다. 그래서 **자기 카메라가 자기 캡슐 머리 부분과 겹쳐 보일 수 있다**(카메라 로컬 Y `1.62`가 캡슐 상단 `1.8`보다 낮다) — 버그가 아니라 알려진 한계다. 거슬리면 다음 스프린트에서 전용 Layer + `Camera.cullingMask`로 처리한다.

**확인**: 프리팹 편집 모드 상단 `<` 로 나오면, `Player.prefab`이 저장된다.

### 10-4. PlayerSpawner에 프리팹 연결

1. Hierarchy에서 `NetworkManager` 선택 → `Player Spawner` 컴포넌트
2. `Player Prefab` 필드에 **`Assets/_Project/Prefabs/Player.prefab`을 드래그**
3. `Spawns` 배열: **비워 둔다**
   - 비어 있으면 PlayerSpawner가 **프리팹 자신의 Transform 위치**에서 스폰한다(`SetSpawnUsingPrefab`). 즉 프리팹의 위치 필드가 곧 스폰 위치다
   - 프리팹 위치를 스폰 지점 `(12, 0.05, 27)`로 두려면: 프리팹 편집 모드에서 루트 Transform Position을 그 값으로 설정하거나, `Spawns`에 빈 오브젝트를 만들어 그 위치를 지정
   - **주의**: 여러 명이 접속하면 전원 같은 지점에 겹쳐 스폰된다. 지금은 동기화 확인이 목적이라 문제없지만, 여러 스폰 지점이 필요하면 빈 오브젝트 몇 개를 만들어 `Spawns`에 넣는다

### 10-5. 씬에서 기존 Player 인스턴스 제거

이제 플레이어는 PlayerSpawner가 런타임에 스폰하므로, 씬에 미리 놓인 인스턴스는 **중복**이다.

1. Hierarchy의 씬 `Player`(프리팹 인스턴스) 선택 → **삭제**
2. 걱정되는 부분 — 씬 컴포넌트 3개가 이 Player를 참조하고 있었다:
   - `PulseSystem`의 `Local Pulse Pipeline Behaviour`·`Pulse Visual Renderer`, 배수로의 `Escape Point Trigger`
   - **이미 코드에서 해결됨**: 세 컴포넌트는 스프린트 8에서 `LocalPlayerRegistry.WhenReady()` 지연 바인딩으로 바뀌었다. 스폰된 플레이어가 자기 자신을 등록하면 자동으로 연결된다. 인스펙터에 빈 참조가 남아 있어도 무방하다(런타임에 덮어씀)

### 10-6. 로컬 멀티 클라이언트 테스트 준비

FishNet 기본 방식으로 **에디터를 호스트, 빌드를 클라이언트**로 붙인다.

**빌드 만들기**:
1. `File > Build Settings` → `Game` 씬이 목록에 있고 체크됐는지 확인
2. `Build` → 아무 폴더에 `Marco.exe` 생성

**접속 — 정식 경로(§12.2 MainMenu)**

> ⚠ **스프린트 19에서 변경됨.** 이 절은 원래 임시 도구 `DebugTools/NetworkTestBootstrap`의 H/J 키를 안내했다. 로비 실기 검증이 끝나 **그 도구와 `Marco.DebugTools` 어셈블리, `Game.unity`의 오브젝트를 모두 제거**했다. 아래는 그 자리를 대신하는 정식 흐름이며, 이 문서의 다른 절에 남아 있는 "H/J로 접속" 안내도 전부 이 절차로 읽으면 된다.

접속은 **`Boot` 씬에서 시작**한다(§15.1 `Boot → MainMenu → Lobby → Game`).

- **H 키**: 방 만들기(호스트) — `MainMenuScreen`이 의도를 남기고 `Lobby` 씬을 로드한 뒤, `LobbyEntry`가 `ConnectionService.StartHost()`를 호출한다(서버+클라이언트 동시 시작)
- **J 키**: 코드 입장(참가) — 같은 흐름으로 `ConnectionService.StartClient("localhost")`
- **왜 로비 씬에 도착한 뒤 접속하는가**: 라운드 상태기계(`RoundNetworkSync`)가 로비 씬의 **씬 NetworkObject**라, 서버가 시작되는 순간 그 씬이 이미 로드돼 있어야 스폰된다
- **어느 창에서 눌러야 하는가**: 키 입력은 **Game 뷰(또는 빌드 exe 창)에 포커스가 있을 때만** 인식된다. 에디터에서는 Play 후 Game 뷰를 클릭해 포커스를 준 다음 누른다
- Console 확인: `[MainMenu] 방 만들기(호스트) 선택 — 로비 씬 로드 후 접속한다` → `[Connection] 호스트로 시작`. **`[NetworkTestBootstrap]` 태그는 더 이상 존재하지 않는다** — 보이면 씬 잔재가 남은 것이다(`Tools/MARCO/Cleanup Debug Tools`)

**절차**:
- **에디터**: `Assets/Scenes/Boot.unity`를 열고 Play → Game 뷰 클릭(포커스) → **H**
- **빌드 exe** 실행 → **J** (`localhost:7770` 접속)

> 이 문서에서 "H/J 접속 없이 Play만 하면…"이라고 적힌 단일 인스턴스 점검들은, 이제 **MainMenu에서 아무 키도 누르지 않거나 `Lobby` 씬을 직접 열어 Play**하는 것과 같다(접속하지 않은 상태라는 뜻은 동일하다).

### 10-7. 검증 (스프린트 8 체크리스트)

| # | 확인 | 기대 |
|---|---|---|
| 1 | 두 클라이언트에서 서로의 캐릭터가 보이는가 | 각 화면에 캡슐/캐릭터 2개 |
| 2 | 한쪽이 WASD로 움직이면 다른 쪽 화면에도 반영되는가 | 약간의 지연 후 원격 캐릭터가 따라 움직임(NetworkTransform) |
| 3 | 원격 캐릭터가 내 입력에 반응하지 않는가 | 내 WASD로 **내 캐릭터만** 움직인다. 원격 캐릭터는 네트워크 값으로만 움직임 |
| 4 | 카메라가 내 것만 켜지는가 | Hierarchy에서 원격 Player의 이름이 `Player (Remote)`, 그 카메라는 비활성. 화면이 섞이지 않음 |
| 5 | 기존 스모크 리그가 여전히 도는가 | 내 캐릭터로 §2(파문)·§7(밸브)·§9(태그) 테스트가 그대로 동작 |

**3·4번이 이번 스프린트의 핵심**이다. `PlayerOwnershipGate`가 소유권을 `FirstPersonController`에 전달해, 원격 캐릭터는 `IsLocallyControlled == false`가 되어 `Update`에서 입력을 건너뛰고 카메라·AudioListener를 끈다. Hierarchy에서 오브젝트 이름이 `Player (Local)` / `Player (Remote)`로 갈리는 것으로 소유권 판정을 눈으로 확인할 수 있다.

**회귀 주의**: 네트워크 없이 그냥 `Game` 씬을 Play하면(빌드 없이 에디터 단독), PlayerSpawner는 서버가 시작돼야 스폰하므로 **플레이어가 안 나올 수 있다**. 이 경우 §10-6의 호스트 시작을 거쳐야 한다. 기존처럼 "그냥 Play하면 바로 걸어다니는" 워크플로우를 유지하고 싶으면, 테스트용으로 씬에 Player 인스턴스를 하나 남겨두는 방법도 있다(그 인스턴스는 `LocalPlayerRegistry`에 자기를 등록하므로 스모크 리그가 그대로 동작한다 — `SetLocalControl`이 안 불려도 기본값이 로컬 조종이라 안전하다).

## 12. 밸브 서버 권위 동기화 (스프린트 10, §14.3)

> **패턴 파일럿**: 밸브 하나를 "클라이언트는 요청만, 서버가 확정" 구조로 옮긴 첫 사례다. 태그·탈출·발소리는 다음 스프린트에서 같은 패턴을 반복 적용한다.
>
> **선행 조건 — 씬 밸브 네트워크화(에디터 1회)**: 밸브를 서버 권위로 만들려면 각 밸브 오브젝트에 `NetworkObject`+`ValveNetworkSync`가 있어야 한다. `NetworkObject`의 SceneId는 에디터가 생성하므로 손으로 못 넣는다 — 아래 도구로 부착한다.
>
> 1. Game 씬을 연 상태에서 메뉴 **`Tools → MARCO → Setup Network Valves`** 클릭 → **계속**
> 2. Console에서 `Valve_Machine/Lifeguard/Boiler` 3개에 NetworkObject/ValveNetworkSync가 부착됐는지 확인
> 3. **씬 저장(Ctrl+S)** — 저장 시 FishNet이 각 밸브의 SceneId를 자동 생성한다. 각 밸브 `Network Object`의 `SceneId`가 0이 아닌지 인스펙터로 확인
>
> (§10의 `Setup Network Player`도 먼저 실행돼 있어야 한다 — 플레이어가 네트워크 스폰되어야 밸브를 돌릴 주체가 생긴다.)
>
> **ObjectId 에러가 뜨면**: `Setup Network Valves`/`Setup Network Player`를 실행한 뒤 FishNet이 ObjectId 관련 에러를 낼 수 있다. 메뉴 `Fish-Networking → Utility → Reserialize NetworkObjects (Prefabs+Scenes)`를 실행해 해결한다.

### 12-1. 로컬 단독 실행 회귀 (네트워크 없이) — 가장 먼저

밸브를 네트워크화한 뒤에도 **네트워크를 시작하지 않으면** 스프린트 5 워크플로우가 그대로여야 한다.

1. 씬에 테스트용 Player 인스턴스를 하나 둔 상태(또는 §10-6 회귀 주의 참고)로 그냥 Play — H/J를 누르지 않는다
2. §7 절차대로 밸브에 접근해 E 홀드 → `[Valve] … 회전 시작/중/개방 완료` 로그가 예전과 동일하게 뜨는지
3. 기대: **네트워크 미시작이면 `ValveNetworkSync`는 스폰되지 않아 `NetworkActive=false`** → 로컬 클라이언트 권위 경로가 그대로 동작. `[ValveNet:*]` 로그는 뜨지 않는다

### 12-2. 2-클라이언트 동기화 (H/J 부트스트랩)

1. §10-6대로 빌드 후, **에디터**에서 Play → Game 뷰 포커스 → **H**(호스트), **빌드 exe** 실행 → **J**(클라이언트)
2. 양쪽 다 플레이어가 스폰되면 각 밸브 `ValveNetworkSync`가 스폰되어 `NetworkActive=true`가 된다
3. **한쪽 클라이언트**에서 밸브에 E 홀드 → 3초 후 개방
4. 기대 로그:
   - 홀드한 쪽(요청자)과 서버(호스트) Console: `[ValveNet:Server] Valve_Machine 상태 Closed → Rotating (홀더=…)`, 이어서 `… 개방 완료 — 서버가 회전 시간을 모두 확정`
   - **반대쪽 클라이언트** Console: `[ValveNet:Client] Valve_Machine 상태 Closed → Rotating — 서버로부터 수신, 화면 반영`, 이어서 `… → Open`
   - **양쪽 모두**에서 `[Valve] 개방 1/3`(`ValveObjectiveTracker`가 브릿지 상태를 읽어 집계) — 밸브를 안 돌린 쪽에서도 개방이 반영되는 것이 이번 스프린트의 핵심
5. **색으로도 확인(스프린트 10 후속)**: 각 밸브 큐브에 `ValveVisualIndicator`가 붙어 색이 바뀐다 — **닫힘=회색, 홀드 중=진행률 따라 회색→노랑 보간, 열림=초록**. 한쪽에서 홀드하면 **양쪽 화면에서** 회색→노랑→초록으로 실시간 변하는지 확인(색 변화는 `ValveBehaviour.State/Progress01`을 읽으며, 그 값이 네트워크면 서버 확정 SyncVar값이라 자동으로 양쪽 동기화됨). Console 로그를 안 봐도 눈으로 동기화를 확인할 수 있다.

### 12-3. 서버 검증 확인 (클라이언트가 임의로 못 바꾼다)

| 시도 | 기대 |
|---|---|
| 클라이언트가 밸브 앞에서 E를 **아주 짧게** 여러 번 깜빡인다 | 서버가 회전 시간(3초)을 채우지 않으면 **개방되지 않는다**. `RepeatedBeginHold_WithoutServerTick_NeverOpens` 테스트가 이 성질을 고정 |
| 한 클라이언트가 홀드 중일 때 **다른 클라이언트**가 같은 밸브에 E 홀드 | 두 번째 요청은 서버가 거부(단일 홀더). 홀더는 최초 시작자 그대로 |
| **메아리(Echo) 역할**로 E 홀드 | 서버가 `Valve.TryBeginRotation`에서 거부(GAP-5) → Rotating으로 안 감 |

> **알려진 한계(GAP-16/17)**: 역할·위치를 아직 서버가 재검증하지 않는다(클라 주장 신뢰). 즉 조작된 클라이언트라면 범위 밖·역할 위조가 가능하다 — 이번 파일럿은 "서버가 타이머·상태의 최종 결정권을 가진다"는 골격만 세운다. 위치/역할 스푸핑 방지는 후속 스프린트(§14.4-3 "안티치트 과투자 금지" 방침).

### 12-4. (수정됨) 연결 전 NullReferenceException

실기 검증 중 발견돼 수정된 문제: `Reserialize NetworkObjects`로 ObjectId 에러를 해결한 뒤에도, **Play는 됐지만 아직 H/J로 접속하기 전** 상태에서 `ValveNetworkSync.NetworkActive`(→ FishNet `IsSpawned`)가 매 프레임 NRE를 던져 Console을 도배하던 버그. 원인은 FishNet의 `NetworkObject` 캐시가 컴포넌트 초기화 전에는 null인데 `IsSpawned`/`IsServerStarted`가 그걸 그대로 역참조하기 때문. `NetworkActive`에 `NetworkObject != null` 가드를 추가해 연결 전(로컬 단독 실행 포함)에는 예외 없이 false를 반환하도록 고쳤다. 다시 이 증상이 보이면 회귀이니 보고할 것.

## 13. 태그 서버 권위 동기화 (스프린트 11, §3.1/§14.3)

> **패턴 반복**: 밸브(§12)에서 확립한 "클라이언트는 요청만, 서버가 확정"을 태그에 적용. 밸브와 다른 점은 (a) 두 주체(술래+대상), (b) 서버가 **거리도 재검증**, (c) 확정 시 대상의 **역할이 Echo로 전환**된다는 것.
>
> **선행 조건 — Player 프리팹에 TagNetworkSync 부착(에디터 1회)**: 태그 대상은 실제 플레이어이므로 Player 프리팹에 `TagNetworkSync`(NetworkBehaviour)가 있어야 한다. NetworkBehaviour의 ComponentIndex 등은 FishNet이 관리하므로 손으로 못 넣는다 — 도구로 붙인다.
>
> 1. 메뉴 **`Tools → MARCO → Setup Network Player`** 재실행 → **계속** (멱등: 기존 컴포넌트는 두고 `TagNetworkSync`만 추가)
> 2. Console에서 `Player 프리팹에 TagNetworkSync 부착` 로그 확인
> 3. **`Fish-Networking → Utility → Reserialize NetworkObjects(Prefabs+Scenes)` 실행** — 프리팹에 NetworkBehaviour를 추가했으므로 인덱스 재구성이 필요할 가능성이 높다(§12 밸브 때와 같은 이유). ObjectId 에러가 나면 반드시 실행.

### 13-1. 로컬 단독 실행 회귀 (네트워크 없이) — 가장 먼저

네트워크화 후에도 **네트워크를 시작하지 않으면** 스프린트 7 태그 워크플로우(§9)가 그대로여야 한다.

1. §9대로 `Role`을 `Seeker`로 두고 Play(H/J 누르지 않음). **대역 러너 `Runner_A/B/C`를 활성화해 둘 것**(스프린트 15에서 비활성화됨 — §9 상단 주의 참고)
2. 대역 도망자(민트 캡슐 `Runner_A/B/C`)에 1.2m 접근 → `[Tag] 태그 — targetId=101 메아리로 전환 (§3.1) [1/3]` 로그
3. 기대: 네트워크 미시작이면 대역은 즉시 확정(로컬 경로 그대로). `[TagNet:*]` 로그는 뜨지 않는다. §9-3·9-4(일부/전원 태그) 동작도 동일

### 13-2. 2-클라이언트 태그 동기화 (H/J)

1. §12 절차로 밸브·플레이어 네트워크 셋업 완료 상태에서, 빌드 후 **에디터=호스트(H)**, **빌드 exe=클라이언트(J)** 접속
2. 술래는 **서버가 자동 배정**한다(§15-2, GAP-22상 호스트가 술래). 수동 지정 키는 스프린트 15에서 제거됐다
3. 술래가 다른 쪽 플레이어(러너)에게 **1.2m 접근**
4. 기대 로그:
   - 서버(호스트) Console: `[TagNet:Server] targetId=… 태그 확정 — 서버 재검증 통과`
   - **러너 쪽 클라이언트** Console: `[TagNet:Client] targetId=… 메아리로 전환 — 서버 확정 수신, 화면 반영 (§3.1)`
   - 양쪽에서 `[Tag] 태그 — targetId=… 메아리로 전환 (§3.1) [N/3]`(각 피어의 RoundCoordinator가 서버 확정 태그를 집계)
5. **핵심(§5.2)**: 태그당한 **러너 쪽 화면에서도** 자신의 역할이 Echo로 바뀐다 — 이후 그 러너는 밸브를 돌릴 수 없고(GAP-5), 다시 태그되지도 않는다

### 13-3. 서버 재검증 확인 (§5.3)

| 시도 | 기대 |
|---|---|
| 술래가 러너에게서 **1.2m보다 멀리** 떨어진 채로 접근 판정 경계에서 요청 | 서버가 거리 재검증(`ServerTagDriver.Validate`)에서 거부 → 태그 안 됨. `Repeated… OutOfRange_IsRejectedByServer` 테스트가 고정 |
| 이미 태그된(메아리) 러너에게 다시 접근 | 서버가 이미태그됨으로 거부(§3.1) |
| 술래가 아닌 클라이언트에서 태그가 발동하는가 | 발동 안 함 — `TagDetector`가 로컬 술래일 때만 요청(소유권 가드) |

> **알려진 한계(GAP-18)**: 술래의 역할·위치는 아직 서버가 완전히 신뢰한다(role은 로컬 필드, 위치는 클라 권위 NetworkTransform). 서버가 재검증하는 건 "대상 역할·거리·이미태그됨"이다. 술래 역할·위치 스푸핑 방지와 전원태그 분모(실제 러너 수)는 라운드/역할 배정 네트워크화(다음 스프린트) 몫이다.

### 13-4. 전원 태그 판정 (§5.4)

각 피어가 **서버 확정 태그만** 집계하므로 태그 카운트는 양쪽에서 일치한다. 전원태그 판정은 스프린트 12(GAP-19)에서 고정 분모를 버리고 "태그 안 된 러너가 0명인가"로 바뀌었고, 스프린트 15에서 대역 러너를 비활성화해 모집단이 실제 플레이어뿐이 됐다 — 2인 테스트에서 러너 1명을 태그하면 곧바로 `SeekerWin`이다.

### 13-5. 연결 전 NRE 회귀 확인

§12-4의 NRE는 태그에도 같은 가드를 **처음부터** 넣었다(`TagNetworkSync.NetworkActive`도 `NetworkObject != null` 선검사). Play 후 접속 전 대기 상태에서 Console에 NRE가 없어야 정상이다(있으면 회귀).

## 14. 라운드 결과 서버 권위 동기화 (스프린트 12, §6.2/§6.3/§14.3)

탈출·라운드 타이머·최종 판정을 서버 하나가 결정하고 전 클라이언트가 **동일한 결과**로 끝나는지 확인한다. 지금까지 각 클라이언트가 독립적으로 판정하던 것을 서버 단일 판정으로 통일했다.

### 14-1. 에디터 셋업 (1회)

1. Game 씬을 연다.
2. **`Tools → MARCO → Setup Network Round`** 실행 → 계속. `RoundCoordinator` 오브젝트에 `Network Object`+`Round Network Sync`가 부착된다.
3. **씬 저장(Ctrl+S)** — `NetworkObject.SceneId`가 0이 아닌 값으로 자동 생성된다.
4. **`Fish-Networking → Utility → Reserialize NetworkObjects (Prefabs+Scenes)`** 실행(씬에 새 NetworkObject를 추가했으므로 스프린트 10 밸브와 동일하게 필요할 가능성이 높다).
5. `Round Network Sync` 인스펙터의 `Round Duration Seconds`가 `600`(§6.2 4인)인지 확인 — 로컬 `RoundTimer.FourPlayerSeconds`와 같은 값이어야 한다.

### 14-2. 접속

`H`로 호스트(에디터), 빌드 exe로 `J` 클라이언트 접속(§10-6 절차 그대로). 접속 직후 호스트 Console에 `[RoundNet:Server] 라운드 시작 — 서버 권위 타이머 600초`가 뜬다.

### 14-3. 타이머 동기화 확인

양쪽 Console에서 `[Round] 남은 시간 NNN초 (서버 권위)`가 **같은 값**으로 줄어드는지 본다(각자 독립적으로 도는 게 아니라 서버 SyncVar를 따른다). 클라이언트가 늦게 접속해도 서버의 현재 남은 시간에 맞춰진다.

### 14-4. 시나리오 A — 탈출 승리 (RunnersWin)

1. 러너로 밸브 3개를 모두 연다(§12 절차, 게이트 개방).
2. 러너가 배수로 출구(EscapePoint)에 도달한다.
3. 호스트 Console: `[RoundNet:Server] 탈출 확정 — playerId=… (누적 1명)` → `[RoundNet:Server] 라운드 종료 판정 = RunnersWin — 전 피어 전파`.
4. **양쪽** Console에서 `[Round] 라운드 종료(서버 확정) — 판정: RunnersWin`이 뜨는지(동일 결과) 확인.

### 14-5. 시나리오 B — 시간 초과 승리 (SeekerWin)

`Round Duration Seconds`를 짧게(예: 20초) 줄여 테스트하면 편하다. 시간이 0이 되면 양쪽에서 **동시에** `판정: SeekerWin`으로 끝나는지 확인한다. (독립 타이머라면 드리프트로 종료 시점이 어긋나지만, 서버 권위면 같은 프레임 전파다.)

### 14-6. 시나리오 C — 전원 태그 승리 (SeekerWin)

호스트가 서버 배정으로 술래가 된 상태에서(§15-2 자동 배정) **러너 전원**을 태그한다. 스프린트 15에서 씬 대역 러너를 비활성화했으므로 모집단은 **실제 접속 플레이어뿐**이다 — 2인 테스트라면 원격 러너 1명만 태그하면 전원 태그가 성립한다. 전원 태그 순간 양쪽에서 `판정: SeekerWin`으로 즉시 종료되는지 확인.

### 14-7. 게이트 미개방 탈출 거부 (서버 재검증)

밸브를 다 열지 않은 상태에서 러너가 탈출 지점에 가면, 호스트 Console에 `[RoundNet:Server] 탈출 거부 — … (gateOpen=False) §5.3`이 떠야 한다(클라 사전 필터 + 서버 재검증 이중). 라운드는 종료되지 않는다.

### 14-8. 로컬 단독 실행 회귀 (스프린트 6 보존)

H/J로 **접속하지 않고** Play만 하면 `Round Network Sync`가 스폰되지 않아 `NetworkActive=false`다. 이때 `RoundCoordinator`는 기존 로컬 타이머·판정 경로로 동작해야 한다(§8 절차 그대로). 연결 전 대기 상태에서 Console에 NRE가 없어야 정상(스프린트 10 가드를 처음부터 넣음).

## 15. 역할 배정 네트워크화 (스프린트 13, §6.2/§14.3 `RoleAssigned`)

서버가 §6.2 표대로 역할을 자동 배정하고, 모든 피어가 같은 역할을 인지하는지 확인한다. (스프린트 15에서 수동 지정 키 K/R을 제거했으므로 **자동 배정이 유일한 경로**다.)

### 15-1. 에디터 셋업 (1회)

1. **`Tools → MARCO → Setup Network Player`** 재실행 → Player 프리팹에 `Role Network Sync`가 추가된다(기존 컴포넌트는 멱등하게 유지).
2. **`Fish-Networking → Utility → Reserialize NetworkObjects (Prefabs+Scenes)`** 실행 — 프리팹에 `NetworkBehaviour`를 추가했으므로 ComponentIndex 재구성이 필요하다(스프린트 11 `TagNetworkSync`와 같은 이유).
3. 씬 저장(Ctrl+S). Player 프리팹 인스펙터에 `Role Network Sync`가 붙어 있고, `Round Network Sync`(씬, §14-1)도 그대로인지 확인.

### 15-2. 자동 배정 확인 (핵심)

`H`로 호스트 시작 → 빌드 exe로 `J` 접속. **K/R을 누르지 않는다.**

호스트 Console 기대 로그:
```
[RoleNet:Server] ownerId=0 역할 배정 = Seeker (§6.2)
[RoleNet:Server] ownerId=1 역할 배정 = Runner (§6.2)
[RoleNet:Server] 역할 배정 완료 — 인원 2명 (술래 1 / 러너 1, §6.2 표)
```
클라이언트 Console: `[RoleNet:Client] ownerId=… 역할 반영 = … — 서버 배정 수신`이 **양쪽 플레이어 모두에 대해** 뜬다.

> **호스트가 술래가 되는 것이 정상이다**(GAP-22: OwnerId 오름차순 첫 1명). 나중에 접속한 쪽은 항상 러너다.

### 15-3. 상대 역할 인지 확인

호스트(술래)에서 `[Tag:Diag]` 로그(§13 진단)를 보면 **`네트워크러너=1`** 이어야 한다 — 원격 플레이어가 배정된 Runner로 인식된다는 뜻이다. 스프린트 12에서 이 값이 0이었던 원인(프리팹 `_role` 기본값)이 이제 서버 배정으로 대체됐다.

### 15-4. 태그 전환 공존 확인 (스프린트 11 회귀)

호스트(술래)가 원격 러너에게 1.2m 접근 → 태그 확정. 확인할 것:
- `[TagNet:Client] … 메아리로 전환` 후 **역할이 Echo로 유지**되고, 초기 배정(Runner)으로 되돌아가지 **않는다**(Echo 가드).
- 이후 새 플레이어가 접속해 재배정이 돌아도 메아리는 그대로 Echo다.

### 15-5. 배정 역할 기준 판정 확인

- **밸브 GAP-5**: 메아리가 된 플레이어가 `E`로 밸브를 돌리려 하면 거부돼야 한다(`[ValveNet:Server]` 로그).
- **전원태그 GAP-19**: 배정된 러너 전원이 태그되면 `SeekerWin`으로 종료. 스프린트 15에서 씬 대역 러너를 비활성화했으므로 모집단은 실제 접속 플레이어뿐이다(대역을 다시 켜면 그들도 모집단에 포함되니 주의).

### 15-6. 로컬 단독 실행 회귀 (GAP-21)

H/J 접속 없이 Play만 하면 플레이어가 1명이라 **배정이 일어나지 않고** 기본값 Runner가 유지된다(§6.2 최소 2인 미만). 밸브·탈출·태그 로컬 워크플로우(§7~9)가 그대로 동작해야 한다. Console에 `[RoleNet:*]` 로그가 없는 것이 정상이다.

## 16. 발소리 파문 네트워크화 (스프린트 14, §5.6/§14.3)

로컬 스모크 리그(고정 청취자)로만 돌던 파문이 **실제 다른 플레이어에게 전달**되는지 확인한다. 지금까지의 SyncVar 방식과 달리 **청취자별 개별 전송(TargetRpc)** 이라, 같은 발소리가 사람마다 다르게 보이는 것이 정상이다.

### 16-0. ⚠️ 먼저 셋업 상태를 점검한다 (실기 1차 실패의 원인)

**`Tools → MARCO → Diagnose Network Setup`** 을 실행한다. 씬·프리팹의 네트워크 컴포넌트 부착 상태와 씬 저장 여부를 한 번에 점검해 Console에 출력한다(아무것도 수정하지 않는 읽기 전용).

> **실기 1차 실패 사례(2026-07-26)**: `Setup Network Pulse`를 실행했는데도 발소리가 원격에 전달되지 않았다. 원인은 **씬에 `PulseNetworkSync`가 실제로 부착되지 않은 것**이었다(씬 파일에서 GUID 0회 확인). 셋업 도구는 씬을 dirty로 표시만 하므로 **저장(Ctrl+S)을 놓치면 변경이 사라지고, 빌드는 저장된 씬을 쓴다.** 이 점검 메뉴가 그 상태를 즉시 잡아낸다.
>
> 증상 판별법: 발소리 파문이 **자기 화면에만** 보이면 로컬 스모크 리그가 계속 도는 것이다 — 네트워크 경로에서는 GAP-1(자기 제외)로 자기 발소리가 **안 보이는 게 정상**이다.

전 항목 ✔이 나온 뒤에 아래 절차를 진행한다.

### 16-1. 에디터 셋업 (1회)

1. **선행 조건 — `Tools → MARCO → Setup Network Player`가 이미 실행돼 Player 프리팹에 `Role Network Sync`가 붙어 있어야 한다**(§15-1). 서버가 청취자 목록을 이 컴포넌트에서 만들기 때문에, 없으면 **아무에게도 파문이 전달되지 않는다.**
2. **`Tools → MARCO → Setup Network Pulse`** 실행 → `PulseSystem` 오브젝트에 `Network Object` + `Pulse Network Sync`가 부착된다.
3. 씬 저장(Ctrl+S) → **`Fish-Networking → Utility → Reserialize NetworkObjects (Prefabs+Scenes)`** 실행.
4. 디버그 로그를 보려면 `Pulse Network Sync` → **`Log Server Deliveries`** 를 켠다(초당 여러 번 도는 경로라 기본 꺼짐 — 검증 시에만 켤 것).

### 16-2. 원격 발소리 전달 (핵심)

`H` 호스트 + `J` 클라이언트 접속. 서로 **6m 이내**(질주 반경)에 서서:

1. 한쪽이 `Shift`+`W`로 질주 이동한다.
2. **다른 쪽 화면**에 T8 파문 링(또는 방위 인디케이터)이 떠야 한다.
3. `Log Server Deliveries`를 켰다면 호스트 Console에 `[PulseNet:Server] Appeared pulse=N → listener=M 개별 전송`이 보인다.

> ⚠️ **반경 주의**(§1과 같은 함정): 걷기는 **2m**, 질주는 **6m**다. 서로 멀리 떨어져 있으면 판정이 `null`이라 아무것도 전달되지 않는 것이 정상이다. 처음 확인할 때는 **바로 옆에서** 시작할 것.

### 16-3. 발생원 자신은 안 보인다 (GAP-1)

이동하는 본인 화면에는 자기 발소리 파문이 뜨지 않아야 한다. 서버의 `SoundPulseResolver`가 `listenerId == sourceId`면 판정을 건너뛰기 때문이다(기존 결정 재사용).

### 16-4. 차폐 전환 — 좌표 → 방위 (GAP-2, 실제 원격 청취자 기준)

T8에서 로컬로 확인했던 것과 같은 검증을, 이번엔 실제 원격 청취자 기준으로 한다:

1. 두 플레이어가 서로 보이는 위치(벽 0개)에서 한쪽이 이동 → 다른 쪽에 **월드스페이스 링**(발생 지점에 원)이 보인다.
2. 발생원이 벽 뒤로 이동 후 다시 이동 → 청취자 화면에서 링이 사라지고 **화면 가장자리 8방위 인디케이터만** 남는다.
3. 하드블로커(`HardBlocker` 태그) 뒤라면 **아무것도 안 보인다**.

이 3단 구분이 §5.6 차폐 판정이 서버에서 청취자별로 돌고 있다는 증거다. 좌표를 공개하지 않는 판정에서는 **좌표가 네트워크로 전송되지도 않는다**(와이어 레벨 GAP-2 강제).

### 16-5. 역할별 인지 배율 (§5.7, 스프린트 13 배정 역할 기준)

술래는 반경 ×1.2, 지속 ×1.5로 인지한다. 확인 방법:
- 호스트가 술래로 배정된 상태(§15-2 자동 배정)에서, 러너가 **질주 반경 경계 부근(6~7m)** 에서 이동한다.
- 술래 화면에는 보이지만, 같은 거리의 다른 러너 화면에는 안 보여야 한다(러너 6m vs 술래 7.2m).
- 이 값이 이제 **로컬 하드코딩이 아니라 서버가 배정한 실제 역할**로 계산된다.

### 16-6. 밸브 소음 전달 (GAP-25, §5.1 12m / §6.1 유인 장치)

한쪽이 `E`로 밸브를 돌리면, **12m 안의 다른 플레이어 화면**에 파문이 떠야 한다(발소리보다 훨씬 넓은 반경). 이게 없으면 §6.1의 "밸브 작업은 술래를 부를지 말지 재는 도박" 설계가 성립하지 않는다.

### 16-7. 로컬 단독 실행 회귀 (스프린트 3~9 보존)

H/J 접속 없이 Play만 하면 `Pulse Network Sync`가 스폰되지 않아 `NetworkActive=false`다. 그러면 기존 로컬 스모크 리그(고정 청취자 id=999)가 그대로 돌아야 한다:
- Console에 `[Pulse] 디버그 청취점 고정: …` 로그가 뜬다.
- §1~6 절차(파문 링·차폐·자연 소멸·`P` 스트레스·`C` 색맹)가 전부 그대로 동작한다.
- `[PulseNet:*]` 로그는 없어야 정상이다.

### 16-8. 부하 확인 (§14.4-2 / §15.5)

`P` 키(스트레스 테스트)를 누르면 파문 30개가 동시 생성된다. 네트워크 모드에서는 위치를 서버가 정하므로 전부 자기 위치에서 발생하지만, **동시 파문 개수 부하**는 그대로 재현된다. 6인 기준 예상 판정량은 초당 10~20회(§5.6 주석)로, 프레임 저하가 체감되면 안 된다.

### 16-9. 진단 로그 해석 — 어느 단계에서 끊겼는지 짚기

전달이 안 될 때 아래 순서로 로그를 확인한다. **위에서 아래로 내려가며 처음 끊긴 곳이 원인**이다.

| # | 로그 | 없으면 원인 |
|---|---|---|
| ① | `[Pulse:Diag] PulseNetworkSync 브릿지를 찾았습니다` | 씬에 `PulseNetworkSync` 미부착 → §16-0 점검 후 툴 실행 + **씬 저장** |
| ② | `[PulseNet:Diag] 스폰 완료 — objectId=…` | NetworkObject가 스폰되지 않음(SceneId 0 / Reserialize 누락) |
| ③ | `[Pulse:Diag] 경로=서버 권위(원격 전달)` | 스폰됐는데 전환 안 됨 — 브릿지의 `NetworkActive`가 false(위 ② 확인) |
| ④ | `[PulseNet:Server] ★ 첫 ServerRpc 수신` | 클라→서버 경로 끊김(RPC 위빙 실패 / 여전히 로컬 경로) |
| ⑤ | `[PulseNet:Diag] 서버 상태 — 청취자=N명` 에서 **N ≥ 2** | 청취자 부족 — Player 프리팹에 `RoleNetworkSync` 없음 또는 소유권 미확정(§15-1) |
| ⑤' | 같은 로그의 `차폐프로브=등록됨` | `PhysicsOcclusionProbe` 미등록 → 판정 자체가 중단(좌표 누출 방지) |
| ⑥ | `[PulseNet:Client] ★ 첫 TargetRpc 수신` | 서버→클라 전송 끊김(TargetRpc 위빙 / 커넥션 조회 실패 경고 확인) |
| ⑦ | 여기까지 다 나오는데 화면에 없음 | 렌더러 문제 — `렌더싱크=등록됨` 확인, 카메라·팔레트·반경(§16-2 주의) 점검 |

`[PulseNet:Diag] 서버 상태` 로그의 **누계 카운터**(`수신 RPC` / `개별 전송`)로 흐름의 양도 볼 수 있다 — 수신은 늘어나는데 전송이 0이면 §5.6 판정에서 전부 걸러진 것(거리·차폐)이다.

### 16-10. "반경이 스펙보다 작아 보인다" 진단 (거리·감쇠 실측)

`[PulseNet:Judge]` 로그(1초 스로틀)가 파문마다 청취자별 실측값을 한 줄로 남긴다:

```
[PulseNet:Judge] type=Sprint 원본반경=6.00m 지속=0.80s source=0 위치=(12.0, 0.1, 27.0) | 청취자 2명
    listener=0(Seeker) → 본인이라 제외(GAP-1)
    listener=1(Runner) 거리=3.42m 역할배율후반경=6.00m 벽=2 감쇠=0.25 인지반경=1.50m → 탈락(차폐 감쇠 후 거리>인지반경)
```

해석 기준:

| 값 | 의미 |
|---|---|
| `원본반경` | 서버가 §5.1 표에서 재계산한 값(GAP-24). **Walk=2m, Sprint=6m, Valve=12m** 중 하나여야 정상 |
| `역할배율후반경` | §5.7 적용값. 청취자가 술래면 ×1.2(6→7.2m), 러너·메아리면 ×1.0 |
| `벽` | 서버 레이캐스트가 센 `Wall` 태그 개수. **열린 공간인데 0이 아니면 레이캐스트 문제** |
| `감쇠` | `0.5^벽수`. 벽1=0.5, 벽2=0.25, 벽3=0.125 |
| `인지반경` | `역할배율후반경 × 감쇠`. 이 값보다 멀면 전달되지 않는다 |

> ⚠️ **중요 — 움직이는 술래는 `Walk`가 아니라 `Sprint`를 낸다**: §5.1은 발소리 등급을 **실제 속도**로 판정하고(걷기 ≤5.0m/s, 질주 >5.0m/s), 술래 기본 속도는 §6.2상 5.4m/s(4인 +8%)다. 따라서 술래가 평범히 걸어도 **질주 등급(6m/0.8s)** 이 발생한다. 술래 발소리의 기대 반경은 2m가 아니라 **6m**다.

`[PulseVis] ★ 첫 시각 오브젝트 생성` 로그는 **화면에서 본 것이 T8 파문인지**를 확정한다 — 표현(월드 링 / 방위 인디케이터)과 실제 색상(RGB+HEX)·색맹 모드를 함께 찍는다. 기본 팔레트의 러너색은 **시안 `#35F0D0`** 이고 색맹 모드에서는 **노랑 `#F2E205`** 다. 밸브 회전 표시는 별개 시스템의 노랑 `(1, 0.9, 0.1)`이므로, 노란 효과를 봤는데 이 로그의 색이 시안이면 **밸브를 본 것**이다.

`[PulseNet:Send] 첫 전송 값 확인` 로그는 판정 반경과 전송 반경이 같은지 확인한다(같은 변수에서 나오므로 불일치는 구조적으로 불가 — 전송 단계 의심을 배제하는 용도).

진단 로그는 `Pulse Network Sync` → `Log Diagnostics`, `Local Pulse Pipeline Behaviour` → `Log Diagnostics`로 각각 끌 수 있다(기본 켜짐).

## 17. 인게임 HUD (스프린트 16, §12.4)

Console 로그로만 보던 정보가 화면에 표시되는지 확인한다. **에디터 셋업이 필요 없다** — HUD는 씬의 `PulseSystem` 오브젝트에 붙은 `In Game Hud` 컴포넌트가 Play 시 자기 UI 계층(Canvas)을 만든다.

> 사전 점검: `Tools → MARCO → Diagnose Network Setup`에 `✔ HUD(스프린트 16): … InGameHud 부착됨 (팔레트 연결됨)`이 나오면 정상이다.

### 17-1. 로컬 단독 실행 표시 확인

Play(H/J 누르지 않음) 후 화면에서:

| 위치 | 기대 표시 | 근거 |
|---|---|---|
| 좌상단 | `⚙ 0/3` + 그 오른쪽에 작은 사각형 3개(전부 어두운 회색) | §12.4 "밸브 카운트 \| 좌상단, 소형 \| 상시" |
| 좌상단 그 아래 | `도망자`(시안) | GAP-26(§12.4 미명시 — 임의 배치) |
| 상단 중앙 | `10:00`에서 1초씩 감소 | §6.2 4인 제한시간 600초 · GAP-26 |

Console에 `[HUD] 빌트인 폰트를 찾지 못했습니다` 경고가 **없어야** 정상이다(있으면 글자가 안 보인다).

### 17-2. 밸브 상태 실시간 반영

1. 밸브에 접근해 `E` 홀드 → 해당 밸브의 사각형이 **진행률만큼 어두운 회색 → 주황(§16.2 `interactable`)으로 밝아진다.**
2. 개방 완료 → 사각형이 주황 최대 + 좌상단 카운트가 `⚙ 1/3`로 증가.
3. 3개 전부 개방 → 좌상단에 `배수로 게이트 개방 — 탈출 가능` 문구 노출(§6.1 이정표, 지금까지 Console 로그로만 보였다).

### 17-3. 색맹 모드 동시 전환 (§19)

`C` 키를 누르면 **파문 색과 HUD 색이 함께** 색맹 팔레트로 바뀌어야 한다(HUD가 T8 렌더러의 토글을 단일 진실 소스로 읽는다). 한쪽만 바뀌면 회귀다.

### 17-4. 결과 배너

라운드가 끝나면 화면 중앙에 `도망자 승리`(시안) 또는 `술래 승리`(레드)가 크게 표시된다(§12.5 승패 배너 색 규칙). 진행 중에는 아무것도 표시되지 않아야 한다. 정식 결과 화면(§12.5 어워드·리매치 투표)은 다음 단계다.

### 17-5. 2-클라이언트 확인

H/J 접속 후 양쪽 화면에서:
1. **타이머가 같은 값**으로 감소(서버 권위 — §14-3과 같은 근거).
2. 역할이 호스트=`술래`(레드), 원격=`도망자`(시안)로 표시(§15 자동 배정 결과가 HUD에 반영되는지).
3. 밸브 카운트가 양쪽에서 동일하게 증가(서버 확정 SyncVar를 읽으므로).
4. 라운드 종료 시 **양쪽에 같은 결과 배너**.

### 17-6. 로컬 폴백 회귀

네트워크를 시작하지 않아도 HUD가 정상 동작해야 한다(로컬 타이머·로컬 밸브 상태·인스펙터 역할값을 그대로 표시). 표시 요소를 끄고 싶으면 `In Game Hud` → `Show Timer`/`Show Valves`/`Show Role`/`Show Gate Hint`/`Show Result Banner` 토글을 쓴다.

## 18. 결과 화면 + 재시작 (스프린트 17, §12.5)

라운드 종료 시 전체 화면 결과가 뜨고, 다음 라운드를 시작할 수 있는지 확인한다. **에디터 셋업 불필요** — `PulseSystem`의 `Result Screen` 컴포넌트가 Play 시 자기 Canvas를 만든다(HUD와 같은 방식).

> 사전 점검: `Tools → MARCO → Diagnose Network Setup`에 `✔ 결과 화면(스프린트 17): … ResultScreen 부착됨`이 나오고, HUD 배너 중복 경고가 없어야 한다.

### 18-1. 로컬 단독 — 결과 화면 표시

가장 빠른 확인법은 시간 초과다: `Round Coordinator` → `Round Duration Seconds`를 20초로 줄이고 Play.

1. 20초 후 → **화면 전체가 어두워지고** 중앙에 `술래 승리`(레드, 대형) + 그 아래 `제한시간이 끝났다`.
2. `어워드 3종 — 다음 단계에서 집계` 플레이스홀더가 흐리게 보인다(§12.5 어워드 자리).
3. 1초 뒤 `Enter — 다음 라운드` 안내가 나타난다(오조작 방지 잠금).

밸브 3개를 모두 열고 배수로로 탈출하면 `도망자 승리`(시안) + `밸브를 모두 열고 배수로로 탈출했다`가 나와야 한다.

### 18-2. 로컬 단독 — 재시작

`Enter`를 누르면:
1. 결과 화면이 사라진다.
2. 타이머가 초기값(설정한 제한시간)으로 되돌아가 다시 감소한다.
3. **좌상단 밸브 카운트가 `⚙ 0/3`으로, 밸브 큐브 색이 회색으로** 돌아간다.
4. Console: `[Round] 라운드 재시작(로컬) — 제한시간 …초, 상태 InGame`.

### 18-3. 진행 중 재시작은 거부된다

라운드 진행 중에는 결과 화면이 없으므로 `Enter`가 아무 일도 하지 않아야 한다. 네트워크 경로에서 강제로 요청이 가면 서버가 `[RoundNet:Server] 재시작 요청 무시 — 라운드가 아직 진행 중이다`를 남긴다.

### 18-4. 2-클라이언트 — 결과 동시성

H/J 접속 후 라운드를 끝내면:
1. **양쪽 화면에 동시에** 결과 화면이 뜬다.
2. 배너·사유 문구가 **양쪽에서 동일**하다(서버가 확정한 `RoundResult`를 읽으므로).
3. 승리 진영 색도 양쪽 동일(§12.5 도망자=시안 / 술래=레드).

### 18-5. 2-클라이언트 — 재시작 전파 (가장 중요)

한쪽에서만 `Enter`를 누른다. 확인할 것:

| 항목 | 기대 |
|---|---|
| 결과 화면 | **양쪽 모두** 사라진다(서버가 `RoundResult`를 `InProgress`로 되돌리므로) |
| 타이머 | 양쪽에서 초기값부터 다시 감소, 값 동일 |
| 밸브 | 양쪽에서 `⚙ 0/3`·회색으로 복구 |
| **역할** | ⚠️ **직전 라운드에서 태그당한 플레이어가 `도망자`로 복구되는지** — 스프린트 17에서 수정한 "메아리 고착" 버그의 회귀 확인 지점이다. `메아리`로 남아 있으면 회귀 |
| 서버 로그 | `[RoundNet:Server] 라운드 재시작 — 타이머 …초, 밸브 3개·태그 N명·역할 N명 초기화` |
| 각 피어 로그 | `[Round] 새 라운드 시작(서버 확정) — 상태 InGame` |

재시작 후 **태그가 다시 정상 작동하는지도** 확인한다(술래가 러너에게 1.2m 접근 → `[TagNet:Server] 태그 확정`). 태그 1회성 가드가 풀리지 않았다면 여기서 실패한다.

> 술래는 재시작 후에도 **같은 사람**이다(GAP-22 결정론적 배정 · §2.2 로테이션은 범위 밖).

### 18-6. 색맹 모드

결과 화면이 뜬 상태에서 `C`를 누르면 배너 색이 §16.2 대체 팔레트로 바뀌어야 한다(HUD·파문과 함께).

## 19. 로비 — 준비·게이팅·리매치 투표 (스프린트 18, §12.2/§12.3/§12.5/§15.4)

**이번 스프린트에서 가장 중요한 실기 검증이다.** "접속 즉시 라운드 시작"이 폐지되고 서버 페이즈(로비→카운트다운→게임→결과→투표)가 진행을 관장한다.

### 19-0. 에디터 셋업 (1회)

1. **`Tools → MARCO → Setup Network Player`** 재실행 → Player 프리팹에 `Ready Network Sync`가 추가된다(⑥).
2. **`Fish-Networking → Utility → Reserialize NetworkObjects (Prefabs+Scenes)`** — 프리팹에 NetworkBehaviour를 추가했으므로 필수(스프린트 11·13과 같은 이유).
3. 씬 저장(Ctrl+S) → **`Tools → MARCO → Diagnose Network Setup`** 전 항목 ✔ 확인(ReadyNetworkSync·ConnectionService·LobbyScreen 포함).

### 19-1. 접속 화면 (§12.2) — 이제 정식 UI 경로다

Play 하면 화면에 "마르코!" + `H — 방 만들기(호스트) · J — 코드 입장(참가)` 패널이 뜬다.
- 키는 같지만 처리 주체가 바뀌었다: `LobbyScreen`(Presentation) → `ConnectionService`(Net).
- Console에 `[Connection] 호스트로 시작` / `클라이언트로 참가`가 찍히는지 확인한다. **(스프린트 19 기준)** 임시 부트스트랩은 제거됐으므로 `[NetworkTestBootstrap]` 태그가 보이면 씬에 잔재가 남은 것이다 — `Tools/MARCO/Cleanup Debug Tools`로 정리한다.

### 19-2. 로비 대기 (§12.3)

H(에디터)+J(빌드)로 접속하면 **라운드가 시작되지 않고** 로비 화면이 뜬다:
1. 방코드 줄(주소 표시 — GAP-28), 플레이어 목록(`○ P0 — 대기 (나)` 형식), `준비완료 (0/2)`.
2. pawn은 맵의 입구 로비(§10.1)에 스폰돼 있고 **자유 이동 가능** — 걸으면 상대 화면에 파문이 전달된다(§12.3 "이 화면 자체가 튜토리얼", 파문은 로비에서도 게이트하지 않음).
3. 이 상태에서 밸브 `E` 홀드 → 서버 Console `[ValveNet:Server] … 홀드 무시 — 라운드 중이 아님(Lobby)`. 태그도 동일하게 거부.
4. HUD 타이머는 제한시간 전체값으로 정지 표시(라운드 시작 전).

### 19-3. 준비 → 카운트다운 → 시작 (§12.3/§15.4)

1. 한쪽만 `R` → 그 줄이 `● P0 — 준비`(시안)로, `준비완료 (1/2)` — **시작되지 않는다**.
2. 양쪽 모두 `R` → `[RoundNet:Server] 전원 준비(2/2) — 3초 카운트다운 시작` → 화면 중앙 `시작까지 3초` 대형 표시.
3. 3초 후: `[RoleNet:Server] 역할 배정 완료` → `[RoundNet:Server] 라운드 시작` → 로비 화면이 사라지고 HUD 타이머가 감소 시작. 역할 표시(호스트=술래)가 이 시점에 나타난다 — **접속 시점이 아니라 카운트다운 완료 시점**이다(스프린트 13과 달라진 점).

### 19-4. 카운트다운 중단 (GAP-29)

양쪽 준비 → 카운트다운 중에 한쪽이 `R`(해제) 시도 → **로비 페이즈가 아니므로 서버가 토글을 무시**한다(`[ReadyNet:Server] … 무시`). 카운트다운 중단은 **이탈**로만 일어난다: 카운트다운 중 한쪽 접속 종료 → `[RoundNet:Server] 카운트다운 중단 — … 로비로 복귀(GAP-29)`.

> 참고: 준비 해제(R)는 **로비 대기 중에만** 가능하다. 로비에서 R을 두 번 누르면 준비→해제로 돌아오는 것을 확인.

### 19-5. 리매치 투표 (§12.5 — GAP-27 해소 확인)

라운드를 끝내면(§18 시나리오 아무거나) 결과 화면 하단이 바뀌어 있다: `리매치? (0/2 찬성) · 15초 · Enter — 찬성`.
1. **한쪽만 Enter** → `(1/2 찬성)` — **재시작되지 않는다**(2인 과반 = 2표).
2. 다른 쪽도 Enter → `[RoundNet:Server] 리매치 가결(2표) — 즉시 재시작 카운트다운` → 3초 카운트다운 → 새 라운드. **로비를 거치지 않는다**(§15.4 가결 → RoleAssign).
3. 재시작 후: 밸브 `⚙ 0/3`·회색 복구, 태그당했던 플레이어 도망자 복구(§18-5와 동일 확인), 타이머 초기값.
4. **부결 경로**: 라운드를 다시 끝내고 15초 동안 아무도(또는 한쪽만) Enter → `[RoundNet:Server] 리매치 부결(15초 만료) — 로비로 복귀, 전원 준비 해제` → 로비 화면 + `준비완료 (0/2)` — 다시 R부터.

### 19-6. 이탈 시나리오 + ⚠ NRE 관찰 (지시서 §1.6 — 반드시 보고)

각 시점에 **상대 클라이언트를 강제 종료**(빌드 창 닫기)하고 호스트 Console을 기록한다:

| 이탈 시점 | 기대 동작 | 함께 관찰할 것 |
|---|---|---|
| 로비 대기 중 | 플레이어 목록에서 즉시 사라짐, `준비완료 (n/1)` 갱신 | ⚠ `NetworkObject.OnDestroy` NRE가 **Play 도중** 뜨는지 |
| 카운트다운 중 | 중단 → 로비 복귀(GAP-29) | 〃 |
| 라운드 중 | 라운드는 계속(최소 인원 중단은 스코프 밖), pawn 소멸 | 〃 |
| 투표 중 | 분모 축소 — 남은 1인의 Enter만으로 가결(1/1) | 〃 |

**NRE가 Play 도중 재현되면**: 스프린트 17에서 "Play 종료 시에만 발생 → 무해"로 보류했던 판단의 재검토 조건이 발동한 것이다. 발생 시점·페이즈·전체 스택을 기록해 보고할 것(벤더 패치 검토 대상).

### 19-7. 로비 완결 흐름 최종 확인

## 20. 씬 분리 — MainMenu·맵 지연 로드 (스프린트 18b, §15.1/§15.4/§12.2)

**이 절은 씬 자산을 실제로 바꾸는 마이그레이션을 포함한다.** 코드는 분리 전/후 모두에서 동작하므로, 도구를 실행하기 전에는 스프린트 18 상태(모든 것이 Game 씬)로 계속 정상 동작한다.

### 20-0. ⚠ 시작 전 백업

`Assets/Scenes/` 폴더 전체를 복사해 둔다. 이 마이그레이션은 `Game.unity`와 `Lobby.unity`를 함께 수정하며, 에디터 Undo로 완전히 되돌아가지 않는다.

### 20-1. 마이그레이션 — **`Setup Everything` 한 번으로 끝낸다**

`Tools → MARCO → Setup Everything (전체 셋업 원버튼)` 하나만 실행한다. 아래 전체가 순서대로 자동 실행되고, **각 단계 사이의 씬 저장까지 코드가 처리**한다(지금까지 `Ctrl+S`를 놓쳐 반복 실패했던 지점을 없앤 것이 이 도구의 핵심 목적이다).

| 순서 | 자동 실행되는 것 |
|---|---|
| 1 | `Scene Flow — 2. Lobby 씬 구성` — NetworkManager·PulseSystem·Main Camera를 Lobby로 이동, `SceneFlow` 오브젝트와 임시 바닥 생성 |
| 2 | `Scene Flow — 5. 로비 배선 정리` — `ConnectionService`를 NetworkObject 없는 오브젝트로 분리(**이게 없으면 접속 자체가 불가능**) |
| 3 | `Setup Network Player` — 활성 씬을 Lobby로 고정한 뒤 실행(NetworkManager 중복 생성 방지) |
| 4 | `Setup Network Valves`(맵) / `Round`·`Pulse`(시스템) |
| 5 | `Scene Flow — 3. 맵 씬 정리` — `SpawnAnchor`를 `(12, 0.05, 27)`에 생성 |
| 6 | `Scene Flow — 4. Boot·MainMenu + 빌드 설정` — Build Settings에 Boot→MainMenu→Lobby→Game 등록 |
| 7 | `Diagnose Network Setup (Lobby + Game 함께)` — 두 씬을 함께 연 상태로 전 항목 점검 |

한 단계라도 실패하면 **그 지점에서 멈추고** 무엇이 실패했는지 Console에 보고한다(다음 단계로 억지로 진행하지 않는다). 각 단계가 멱등하므로 원인을 고친 뒤 다시 눌러도 안전하다.

> ⚠ **남은 수동 단계는 하나뿐**: 마지막에 뜨는 안내에서 **`Fish-Networking → Utility → Reserialize NetworkObjects`** 창을 열고 `Reserialize Prefabs`/`Reserialize Scenes`를 켠 뒤 **Run Task** → 열린 씬 저장. 이 작업만은 코드로 실행할 수 없다(벤더 창의 private 인스턴스 메서드 + 창 상태 의존, 개별 API는 FishNet 내부 전용). **건너뛰면** SceneId가 확정되지 않아 라운드 상태기계가 스폰되지 않는다(스프린트 14 실기 실패와 같은 유형).

개별 도구(`Scene Flow — 1~5`, `Setup Network *`)는 **그대로 남아 있다** — 한 단계만 다시 돌리고 싶을 때 쓴다. 실행 전 `Assets/Scenes` 폴더 백업은 여전히 권장한다.

### 20-6b. 렌더링·성능 확인 (스프린트 18b 실기 버그 재발 감지)

맵이 로드된 InGame 상태에서 확인한다. **원인은 조명이 아니라 카메라 중복이었다** — 마이그레이션이 Game의 `Main Camera`를 Lobby로 옮겼는데 Lobby에 이미 카메라가 있어 전체화면 카메라가 2대가 됐고, 같은 장면을 매 프레임 두 번 그리면서 프레임이 떨어지고 서로를 덮어써 바닥이 검게 깨졌다.

| 확인 항목 | 기대 | 깨졌을 때의 증상 |
|---|---|---|
| 바닥·벽 조명 | 그레이박스가 정상적으로 밝게 보인다 | 바닥이 검게 깨짐 |
| **프레임** | 로비 때와 체감 차이가 없다 | 눈에 띄는 저하(중복 렌더링) |
| Stats 창 `Batches`/`Tris` | 카메라 1대분 | 대략 **2배** |
| Console | AudioListener 중복 경고 없음 | `There are 2 audio listeners...` |
| 클라이언트 화면 | 맵이 보인다 | **하늘만 보이고 멈춤**(플레이어 카메라가 꺼진 상태) |

증상이 보이면 `Tools → MARCO → Diagnose Network Setup (Lobby + Game 함께)`가 `✖ 활성 카메라가 N대입니다`로 잡아낸다. `Scene Flow — 5. 로비 배선 정리`를 실행하면 중복 카메라를 자동 비활성화한다(삭제가 아니라 비활성화라 되돌릴 수 있다).

> **조명·라이트맵은 원인이 아니다**(조사로 확정): Game 씬은 정적 오브젝트가 0개, `m_BakeOnSceneLoad: 0`, 라이트맵 데이터 자산 없음 — **베이크된 라이트맵이 애초에 존재하지 않으므로 재베이크가 필요 없다.** 활성 씬 전환도 FishNet이 자동 처리한다(`SceneManager._setActiveScene` 기본 true → 전역 씬 목록의 첫 씬 = 맵을 활성 씬으로 지정).

**카메라를 고쳤는데도 바닥이 깨져 보이면 두 번째 원인이다 — 머티리얼/URP 불일치.** 프로젝트는 URP로 렌더링하는데 `Assets/_Project/Maps/Graybox/*.mat` 4개가 **빌트인 Standard 셰이더**를 가리키고 있었다. URP는 빌트인 셰이더를 지원하지 않아 그 표면이 정상 조명을 받지 못한다. `Tools → MARCO → Fix Graybox Materials (URP 셰이더 복원)`로 고친다(`Setup Everything`에 포함됨). 이 머티리얼들은 원래 URP/Lit로 작성돼 `_BaseColor` 등 URP 속성값이 남아 있으므로 셰이더만 되돌리면 §16.1 팔레트 색이 함께 복원된다. 진단 도구가 `✖ 머티리얼 N개가 빌트인 Standard 셰이더를 씁니다`로 잡아낸다.

> 참고: 바닥의 `_BaseColor`는 `(0.1, 0.1, 0.1)`로 **설계상 매우 어두운 회색**이다. 정상 복원 후에도 밝지는 않은 것이 정상이며, 벽 `(0.24)`·상호작용 오렌지 `(1, 0.72, 0.3)`와의 대비로 판별한다.

### 20-6d. 로비 임시 바닥 전환 확인 (실기에서 확정된 결합 버그)

로비 임시 바닥(`Lobby Floor`)은 **로비 페이즈의 유일한 지면**이면서, 맵 바닥과 **정확히 같은 평면(y=0)**에 있다. 그래서 항상 켜거나 항상 끄면 반드시 한쪽이 깨진다 — 실기에서 확인된 상관관계다:

| Lobby Floor | 로비 페이즈 | 인게임(맵 로드 후) |
|---|---|---|
| 항상 켜짐 | ✔ 정상 | ✖ 맵 바닥과 **Z-파이팅**(바닥이 밝게 깨져 보임) |
| 항상 꺼짐 | ✖ 지면 없음 → **pawn 무한 낙하**(상대가 접속 안 된 것처럼 보임) | ✔ 정상 |
| **`LobbyPlaceholderFloor` 부착** | ✔ | ✔ |

> 낙하 한계·리스폰 로직이 없으므로(코드 검색 확인) 한 번 떨어지면 돌아오지 못한다. "상대가 접속되지 않았다"고 보이는 증상의 정체가 이것이다.

Play 중 Console에서 전환을 확인한다:
1. 로비 대기: `[SceneFlow] 로비 임시 바닥 ON — 맵이 없어 이 바닥이 지면 역할을 한다(무한 낙하 방지).`
2. 맵 로드 직후: `[SceneFlow] 로비 임시 바닥 OFF — 맵 바닥이 지면을 대신한다(같은 평면 Z-파이팅 방지).`
3. 부결로 로비 복귀: 다시 `ON`

| 확인 항목 | 기대 |
|---|---|
| 인게임 바닥 | 깜빡임·밝은 얼룩 없이 균일한 어두운 회색 |
| 양쪽 플레이어 | 로비·인게임 모두 서로 보인다 |
| 진단 도구 | `✔ 로비 임시 바닥: … LobbyPlaceholderFloor 부착됨` |

### 20-6c. 스폰 분산 확인 (즉시 SeekerWin 재발 감지)

라운드 시작 직후 확인한다. **증상**: 술래와 러너가 같은 자리에 스폰돼 시작 즉시 태그 반경(1.2m) 안에 들어가 곧바로 `SeekerWin`으로 끝난다.

**선행 조건 — 로컬 플레이어 등록이 살아 있어야 한다.** 스폰 분산은 `LocalPlayerRegistry.Current`를 폴링해 동작하므로, 그 값이 비어 있으면 배치 자체가 **한 번도 실행되지 않고** 전원이 프리팹 기본 좌표 `(12, 0.05, 27)`에 남아 시작 즉시 태그된다. Console에서 다음을 확인한다:

```
[PlayerReg] Register('Player', 로컬조종=True) — 이전 Current=없음        ← 내 pawn
[PlayerReg] Register('Player', 로컬조종=True) — 이전 Current=Player      ← 상대 pawn이 덮어씀(정상)
[PlayerReg] Unregister('Player (Remote)', …) 후 실제 로컬 pawn 'Player (Local)'으로 복구했습니다  ← 핵심
```
마지막 줄이 **"복구했습니다"가 아니라 "대체할 로컬 pawn이 없습니다"**로 끝나면 등록이 끊긴 것이고, 그 뒤 `[SpawnDiag] 대기 중 — 로컬 플레이어가 아직 스폰되지 않았습니다`가 무한 반복된다.

> 원인: 모든 pawn이 `OnEnable` 시점에는 `IsLocallyControlled` 기본값(true)이라 **원격 pawn도 자기를 등록**해 `Current`를 덮어쓴다. 소유권 확정 후 원격이 해제되면 `Current`가 비는데, 내 pawn은 이미 true라 `SetLocalControl(true)`가 조기 반환해 재등록되지 않았다. 특히 호스트는 내 pawn의 소유권 확정이 상대 접속보다 **먼저** 끝나 있어 재발행만으로는 복구되지 않는다 — 그래서 해제 시점의 자가 복구가 필요하다.

| 확인 항목 | 기대 |
|---|---|
| 시작 직후 서로의 위치 | **떨어져 있다**(앵커 중심 반경 4m 원 위, 인접 간격 약 3.06m) |
| Console | `[SceneFlow] … 스폰 슬롯 0/8 = (16.00, 0.10, 27.00) … 인접 슬롯 간격 3.06m` — 플레이어마다 **다른 슬롯 번호** |
| 라운드 진행 | 시작 즉시 끝나지 않고 §6.2 제한시간이 흐른다 |

슬롯은 `PlayerId % 슬롯수`로 결정되며 결정론적이라 서버가 좌표를 나눠 줄 필요가 없다. 반경·슬롯 수는 `SceneFlow` 오브젝트의 `Pawn Phase Teleporter`에서 조정하며, **인접 간격이 태그 반경보다 커야 한다** — 이 조건은 `SpawnRingTests`가 코드로 강제한다.

### 20-7. ⚠ NRE 재검토 (스프린트 17 보류 조건 — 반드시 기록)

이번 스프린트는 **맵 언로드**라는 새 시나리오를 추가했다. 씬 언로드는 밸브 3개 등 **다수의 씬 NetworkObject를 한꺼번에 파괴**하므로, 스프린트 17에서 "Play 종료 시에만 발생 → 무해"로 보류한 `NetworkObject.OnDestroy` NRE가 **Play 도중** 나타날 가능성이 가장 높은 지점이다.

관찰·기록할 시점:

| 시점 | NRE 발생 여부 | 비고 |
|---|---|---|
| 맵 언로드(§20-5 부결) | ? | **가장 유력** — 밸브 3개 동시 파괴 |

### 20-8. 분리 전 배치로 되돌리기 (문제 발생 시)

`Assets/Scenes/` 백업으로 복원하면 스프린트 18 상태로 돌아간다. 코드는 그 배치에서도 동작한다 — `SceneFlowController`가 없으면 맵 지연 로드를 건너뛰고(`MapReadyForRound()`가 true) 기존처럼 한 씬에서 전부 진행한다. 즉 **코드 롤백은 불필요**하다.

## 21. 낙하 복구 (스프린트 20, GAP-32)

기획서에 낙하·리스폰 스펙이 없어 최소 안전 구현으로 넣은 기능이다. **맵 밖으로 떨어지면 마지막으로 접지해 있던 위치로 되돌린다.**

### 21-1. 배선 확인

`Tools → MARCO → Diagnose Network Setup (Lobby + Game 함께)` → `✔ 낙하 복구(스프린트 20): FallRecoveryDriver 부착됨`.
없으면 `Scene Flow — 5. 로비 배선 정리` 실행 후 Lobby 씬 저장.

### 21-2. 단일 인스턴스 확인

맵이 로드된 상태(라운드 진행 중)에서 맵 밖으로 걸어 나가거나 떨어진다. 그레이박스 경계가 막혀 있어 자연스럽게 떨어지기 어려우면, Scene 뷰에서 플레이어를 맵 밖으로 끌어 놓아도 된다.

| 확인 항목 | 기대 |
|---|---|
| y가 **-10 아래**로 내려간 순간 | 즉시 복구된다(계속 떨어지지 않는다) |
| 복구 위치 | 마지막으로 **서 있던** 자리(공중에서 지나친 좌표가 아님) |
| Console | `[FallRecovery] 낙하 감지(y < -10) — 마지막 안전 지점 (…) 으로 복구했습니다.` |
| 복구 직후 | 그 자리에 **서 있는다** — 바닥을 뚫고 다시 떨어지면 수직 속도 초기화가 안 된 것이다 |
| 잠수(§4.2) | 물에 들어가도 복구가 발동하지 않는다(킬 플레인이 훨씬 아래) |

### 21-3. 역할 보존 확인 (§0 요구사항)

| 상태 | 확인 |
|---|---|
| 술래로 떨어짐 | 복구 후에도 **술래** — HUD 역할 표시 불변 |
| 러너로 떨어짐 | 복구 후에도 **러너** |
| **태그당한 메아리로 떨어짐** | 복구 후에도 **메아리**(태그 상태가 풀려 러너로 돌아오면 안 된다) |

> 구현상 `FallRecoveryDriver`는 Transform과 수직 속도만 만지고 `IRoleState`/`RoleNetworkSync`/태그 SyncVar에 접근하지 않는다. 역할이 바뀐다면 다른 곳의 회귀다.

### 21-4. 2-클라이언트 확인

한쪽이 떨어져 복구될 때 **상대 화면에서도** 그 캐릭터가 같은 위치로 이동해야 한다(소유자 권위 `NetworkTransform`이 전파). 상대 화면에서 캐릭터가 계속 아래로 사라진다면 전파가 끊긴 것이다.

### 21-5. 알려진 한계 (GAP)

- **GAP-32**: 기획서에 낙하/리스폰 스펙 없음 — 킬 플레인 −10m·기록 주기 0.5초는 임의값이다. 플레이테스트 조정 대상.
- **GAP-33**: 소유자 권위로 처리한다. 이동 자체가 서버 권위로 바뀌면 이 판정도 함께 옮겨야 한다.
- **무적 시간 없음**: 기획서에 명시가 없어 넣지 않았다. 복구 직후 술래가 근처에 있으면 즉시 태그될 수 있다.
