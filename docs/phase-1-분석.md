## 0. 총평

이 기획서는 이미 Phase 1 산출물의 상당 부분을 담고 있다. §9(밸런스 근거), §14~15(네트워크·기술 아키텍처), §20(MVP 정의), §21(로드맵), §23(리스크)은 각각 Studio Producer / Backend Architect / Senior PM / Sprint Prioritizer 산출물에 해당한다. **Phase 1을 처음부터 다시 돌릴 필요 없다.**

특히 강한 부분:

- **§9가 존재한다는 것 자체.** 수치마다 "왜 이 값인가"가 붙어 있어 플레이테스트 후 조정할 때 무엇을 건드리면 안 되는지 판단할 수 있다. 대부분의 1인 기획서에 없는 것.
- **§5.4의 이중 레이어 분리.** "판정"과 "렌더링"을 분리해서 벽 뒤 소리가 투명하게 보이는 모순을 미리 차단했다. 이건 구현 단계에서 반드시 터졌을 버그를 설계로 막은 것.
- **§20.2 제외 목록이 구체적이다.** 스코프 방어선이 명시돼 있어 M3에서 기능이 새는 걸 막는다.

따라서 이 문서의 나머지는 **새 산출물 생성이 아니라 갭 지적**에 집중한다.

## 1. 스펙 갭 (7건) — GAP-1~3 결정 완료, GAP-4~7은 M3 진입 전 확정

### GAP-1 · 본인 파문에 역할 배율이 적용되는가 [심각 → **결정됨**]

§5.3은 "본인 목소리 → 본인 화면"을 0ms 로컬 렌더로 처리하고, 두 경로의 반경·지속시간이 **반드시 일치해야 한다**고 못박았다. 그런데 §5.7은 술래에게 반경 ×1.2, 지속 ×1.5를 적용한다.

술래가 자기 목소리를 냈을 때:

- 로컬 렌더는 마이크 진폭을 직접 셰이더에 바인딩하므로 배율이 안 붙는다 → 반경 9m로 보인다
- 다른 러너 화면에서 그 술래의 파문은 러너 배율 ×1.0 → 9m
- 그런데 **술래 본인이 리스너로서 자기 파문을 본다면** ×1.2 → 10.8m가 되어야 하나?

어느 쪽이든 §5.3의 일치 원칙과 §5.7의 배율 원칙 중 하나가 깨진다.

**결정**: 인지 배율은 **타인이 발생시킨 펄스에만** 적용한다. 본인 파문은 항상 원본값(배율 없음)으로 렌더. 근거 — 배율의 게임적 의미는 "술래는 남의 소리를 더 잘 듣는다"이지 "술래는 자기 목소리를 크게 본다"가 아니다. §5.3의 로컬/원격 렌더 일치 원칙이 §5.7보다 우선한다.

**명세 반영**: §5.7 서술에 "이 배율은 리스너가 타인이 발생시킨 SoundPulse를 수신할 때만 적용되며, 본인이 발생시킨 펄스의 로컬 렌더에는 적용되지 않는다"를 추가. §5.5 `PerceivedPulse`는 본인 발생 펄스에 대해 아예 생성되지 않음(로컬 0ms 경로로만 처리)을 명시.

### GAP-2 · PerceivedPulse가 정확한 소스 좌표를 그대로 보낸다 [심각 → **결정됨**]

§14.3의 `PerceivedPulse` 페이로드에 `sourcePos`가 raw 좌표로 들어간다. 그런데:

- §3.4는 방향 게이지를 일부러 8방위로 스냅해 정밀도를 낮췄다 ("정확한 좌표가 아니라")
- §5.4는 `worldSpaceRingVisible = false`일 때 월드스페이스 링을 안 그린다고 했다

즉 **서버가 "이 리스너는 정확한 위치를 몰라야 한다"고 판정한 상황에서도 클라이언트는 정확한 좌표를 이미 받고 있다.** 화면 가장자리 방향 힌트만 그리기 위해 전체 좌표를 보내는 셈이다.

§14.4에서 "친구 대상이라 안티치트에 과투자하지 않는다"고 했으므로 치팅은 논외로 치더라도, 이건 **설계 의도와 프로토콜이 불일치**하는 상태다. 나중에 공개 매치메이킹을 붙이면 그때 프로토콜을 다시 깎아야 한다.

**결정**: `worldSpaceRingVisible == false`인 경우 `sourcePos` 대신 8방위 스냅된 방향 enum(`DirectionOctant`)만 전송. `worldSpaceRingVisible == true`(§5.4 시네마틱 하이라이트 조건)일 때만 raw 좌표 포함.

**명세 반영**: §5.5 `PerceivedPulse` 구조체를 다음과 같이 변경한다.
```csharp
struct PerceivedPulse {
    float   perceivedRadius;
    float   perceivedDuration;
    Vector3? sourcePos;         // worldSpaceRingVisible == true 일 때만 값 존재
    DirectionOctant direction;  // 항상 존재 (N/NE/E/SE/S/SW/W/NW, §3.4 스냅과 동일 로직)
    bool    worldSpaceRingVisible;
}
```

### GAP-3 · 차폐 판정이 펄스 발생 시점 1회인가, 지속 중 재계산인가 [심각 → **결정됨**]

§5.6 `ResolvePulseForListener`는 단발 함수로 서술돼 있다. 그런데 고함은 2.5초(술래 기준 3.75초) 지속된다. 그 사이 리스너가 벽 뒤에서 걸어 나오면?

- **1회 계산이면**: 벽 뒤에 있던 순간 판정으로 차단 → 나와도 파문이 안 보인다. 플레이어 입장에서 "분명 눈앞에서 났는데 안 보임"
- **매 프레임 재계산이면**: §5.6에서 계산한 "초당 10~20회 레이캐스트" 견적이 무너진다. 지속 3.75초 × 60fps × 리스너 5명 = 펄스 하나당 1,125회

**결정**: 발생 시점 1회 판정 + **지속 중 0.25초 간격 재판정**(펄스당 최대 15회). 6인 기준 초당 30~60회 레이캐스트로 §5.6이 원래 견적한 "10~20회" 대역에 근접하게 유지된다. 벽 뒤에서 나오는 케이스도 최대 0.25초 지연으로 잡힌다.

**명세 반영**: §5.6 `ResolvePulseForListener` 의사코드에 재판정 루프 추가.
```
on pulse created:
    result = ResolvePulseForListener(pulse, listener)   # 최초 1회
    if result != null: emit(result)

every 0.25s while pulse.active:
    result = ResolvePulseForListener(pulse, listener)   # 재판정
    if result changed from last: emit(update)
```
M1 스파이크(§15.5 우선순위 1)에서 이 주기로 6인 기준 프레임타임 영향을 실측해 확정한다(목표 <1ms, 아래 T6).

### GAP-4 · 방향 게이지와 차폐의 관계가 없다 [보통]

§3.4는 대화·고함 등급에서 방향 게이지가 뜬다고만 한다. §5.6 차폐로 걸러진 이벤트에 대해서도 뜨는지 명시가 없다.

§5.4 표에서 "판정 레이어를 통과한 경우에만 이후 렌더링 진행"이라 했으니 논리적으로는 안 떠야 한다. 하지만 §3.4에는 그 연결이 안 적혀 있고, 하드블로커(무대 커퍼)는 아예 이벤트를 미전송하므로 게이지도 당연히 안 뜬다 — 이건 §11.2의 "숨는다의 정의를 확장" 의도와 일치한다.

**권장**: §3.4에 한 줄 추가 — "방향 게이지는 §5.6 판정을 통과한 펄스에 대해서만 트리거된다."

### GAP-5 · 메아리가 밸브를 돌릴 수 있는가 [보통]

§3.2는 메아리를 "벽 통과, 충돌 없음, 능력은 노크"로 정의한다. 밸브 상호작용 가능 여부가 없다. 유령 설정상 불가가 자연스럽지만, 명시가 없으면 구현자(=Claude Code)가 임의 판단한다.

더 중요한 건 **§13.3의 밸런스 영향**이다. 러너가 이탈하면 즉시 메아리로 전환하되 "6.2 밸런스 표 유지, 재계산 없음"이라 했다. 4인 게임에서 러너 3명 중 1명이 이탈하면 밸브 3개를 2명이 돌려야 한다. 밸브당 3초 × 12m 반경 노출을 감안하면 난이도가 급상승한다.

**권장**: 메아리는 밸브 상호작용 불가로 명시. 이탈로 인한 난이도 상승은 의도된 페널티로 두되, M3 플레이테스트에서 "이탈 발생 라운드의 술래 승률"을 별도 집계해 §6.3의 40~60% 구간 검증에서 제외할지 판단.

### GAP-6 · §5.2 캘리브레이션이 MVP 포함 목록에 없다 [보통]

§5.2 본문은 "개인 baseline 보정은 **MVP 필수 항목으로 승격**한다"고 명시했다. 그런데 §20.1 포함 목록에는 "5.8 VAD 파이프라인 전체"만 있고 §5.2가 없다.

§12.2의 "솔로 연습장(마이크 캘리브레이션 겸용)"과 §12.6 오디오 탭의 "발화 강도 재보정" 버튼이 있으니 실질적으로는 포함된 것으로 보이나, 태스크 리스트를 뽑을 때 누락되기 쉽다.

**권장**: §20.1에 "5.2 음성 분류 파이프라인 전체(대역 필터·연속성 검사·개인 캘리브레이션 포함)" 명시.

### GAP-7 · M3 6주에 설정 화면 전체가 들어간다 [보통]

§20.1 MVP 포함 목록에 설정 화면 4개 탭(§12.6) 전체 + 키 리바인딩 + 색맹 모드가 들어있다. §21 기준 M3는 5~10주차, 즉 **6주**다. 이 6주에 들어가야 하는 것:

맵 1개 · 4인 네트워킹 · 밸브/탈출 루프 · VoIP + 3등급 분류 · 차폐 시스템 · 인지 배율 · VAD 파이프라인 · 1인칭 조작 · 찰칵이 · 방코드 입장 · 결과 화면 · **설정 4탭 + 리바인딩 + 색맹**

1인 개발 기준으로 마지막 항목이 가장 먼저 잘릴 후보다. 그런데 §19에서 색맹 모드를 MVP 접근성 대응으로 명시했으므로 뺄 수 없다.

**권장**: 설정 화면을 두 단계로 쪼갠다.
- **M3 필수**: 오디오 탭(마이크 장치·게인·재보정) + 색맹 토글 + 마우스 감도. 이 3개는 게임이 안 돌아가거나 접근성이 깨진다.
- **M4로 이월**: 키 리바인딩 전체, FOV 슬라이더, 밝기, 프레임 표시. §20.3 합격 기준("친구 4인이 9판 연속 플레이")에 영향 없다.

### 2.2 어셈블리 분리 (§15.2) 검토

`Core / Net / Presentation` 3분할은 타당하다. 다만 한 가지:

`SoundPulseSystem`이 §15.3에서 "이벤트 생성 → 차폐 판정 → 배율 적용 → PerceivedPulse 송신"을 담당한다. 이건 Core인데 `Physics.Linecast`(UnityEngine.Physics)에 의존하고, 동시에 파문 렌더링(Presentation)과 물려 있다.

**권장**: `SoundPulseSystem`을 둘로 나눈다.
- `Core.SoundPulseResolver` — 순수 판정 로직. Physics는 인터페이스(`IOcclusionProbe`)로 주입받아 **테스트에서 목킹 가능**하게
- `Presentation.PulseRenderer` — PerceivedPulse 수신 → 셰이더 파라미터 바인딩

차폐 규칙은 이 게임의 심장이고 §9 밸런스가 전부 여기 걸려 있다. 벽 개수별 감쇠(×0.5^n)와 하드블로커 처리는 유닛 테스트로 고정해두는 게 값싸다. Physics를 직접 부르면 테스트를 못 쓴다.

### 2.3 기술 리스크 (§15.5) 재평가

§15.5의 우선순위 1(파문 렌더 성능)에 동의한다. 다만 **측정 대상이 하나 빠졌다.**

§15.5는 "동시 파문 100개 @ 60fps"를 목표로 잡았는데, 4인 기준 초당 발생 2~4개 × 지속 최대 3.75초면 동시 파문은 **15개 안팎**이다. 100개는 과도하게 보수적이라 M1에서 불필요한 최적화에 시간을 쓸 수 있다.

**권장**: M1 목표를 "동시 파문 30개 @ 60fps"로 낮추고, 남는 시간을 GAP-3(차폐 재판정 주기) 실측에 쓴다. 100개는 6인 + v1.x 8~10인 대비 스트레스 테스트로 M4에 배치.

### 순서 근거

- **6주차에 사운드 코어를 최우선 배치**한 것은 §15.5의 리스크 1과 일치한다. T5~T8이 실패하면 게임이 성립하지 않으므로 5주차 코어 루프 직후 즉시 검증한다.
- **T9(음성 파이프라인)를 T5(차폐)보다 뒤에** 둔 이유: 차폐 로직은 마이크 없이 더미 펄스로 테스트 가능하다. 음성 입력이 막혀도 차폐 검증은 진행된다.
- **T25가 10주차 전체를 잡아먹는다.** 9판을 돌리려면 최소 2~3세션이 필요하고, §20.3은 "하나라도 미달이면 §9 코어 수치부터 손댄다"고 했으므로 수정 시간이 필요하다.

## 5. 예산 제약 — 제작비용 $0

기존 §22(스팀 출시 전략)는 판매 전략만 다루고 "제작 과정 자체에 돈을 쓰지 않는다"는 제약은 문서에 없었다. 이 프로젝트는 **M1~M4(제작 전 기간) 현금 지출 0원**을 전제로 재점검한다.

### 5.1 이미 무료인 것 (변경 불필요)

| 항목 | 상태 | 근거 |
|---|---|---|
| Unity 6 | 무료 | Personal 라이선스 — 연 매출 20만 달러 미만이면 무료. §22 목표(위시리스트 7,000, 첫 주 매출)로는 한참 못 미침 |
| FishNet | 무료 | 오픈소스(MIT 계열), §14.1에서 이미 "무료"로 명시 |
| Facepunch.Steamworks | 무료 | 오픈소스 바인딩. Steamworks SDK 자체도 무료 배포 |
| ProBuilder | 무료 | Unity 공식 패키지, §16.3에서 이미 사용 중 |
| Steam Voice API | 무료 | Steamworks SDK에 포함 |

이 5개는 기획서가 이미 올바르게 선택했다. 손댈 것 없음.

### 5.2 유료를 가정했을 수 있는 항목 → 무료 대체

### 5.3 유일한 불가피 비용 — Steam Direct 등록비

§21 M6(21~26주차, "EA 출시")와 §22(스팀 출시 전략)에 도달하면 **Steam Direct 앱당 $100(1회, 최초 판매 수익으로 환급됨)**이 발생한다.

이건 "제작비용"이 아니라 **유통비용**이다 — M1~M5(제작·MVP·에셋·데모)까지는 발생하지 않고, M6에서 실제 스토어 페이지를 만드는 시점에만 필요하다. 대안:

- **itch.io**: 등록비 0원, 무료 배포 또는 pay-what-you-want로 M5(§21 데모·Next Fest 준비) 단계까지 완전 무료 검증 가능
- Steam Direct $100은 EA 출시를 실제로 결정하는 시점(M6)까지 지출을 미룰 수 있고, §22에 이미 "출시 전주 초반 -10%" 등 판매 전략이 있어 첫 판매로 즉시 회수됨

**권장**: §21 로드맵에 "M6 착수 조건: Steam Direct $100 지출 결정"을 명시적 체크포인트로 추가. 그 전까지는 itch.io 데모로 M1~M5를 완전 무료로 진행.

### 5.4 §22 갱신 — 무료 제작 전제 명시

§22 표의 "가격/데모/얼리액세스 패스" 항목은 그대로 유효하다(이건 판매 전략이지 제작비용이 아님). 다만 문서에 다음 한 줄을 추가해야 향후 혼동이 없다:

> **제작비용 원칙**: M1~M5(제작·MVP·데모)는 현금 지출 0원으로 진행한다. Steam Direct $100은 M6(EA 출시 결정) 시점에만 발생하며, 그 전까지 itch.io 무료 배포로 검증한다.

### 5.5 게이트 영향

이 재점검으로 §4 게이트 기준 4번("예산 승인")이 ⚠에서 ✅로 확정됐다. 기획서가 처음부터 무료 스택(Unity/FishNet/Facepunch)을 골랐기 때문에 실제로 막힐 게 없었고, 빠진 건 "무료로 진행한다"는 제약을 문서에 명문화하는 것뿐이었다.
